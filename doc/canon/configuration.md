# Конфигурация и данные Canopus

Решения владельца, чат задач 285–286, 2026-11-06: независимые приложение и плагин; обычный запуск без настроек; один явный выбор файла; пять публичных полей приложения и десять проектных полей плагина. Уточнение владельца: «согласен, но убранные настройки должны переехать в константы в коде, в будущем мы можем вернуться опять к варианту в настройках». Малый маршрут не ограничен временем.

## Выбор экземпляра

Приложение запускается командой `canopus` (равнозначно `canopus serve`). По умолчанию оно читает `<home>/.canopus/config.json`; `--config <file>` выбирает другой файл. Относительный CLI-путь разрешается от текущего каталога. **Родитель выбранного файла — корень экземпляра**: там лежат `secrets.json`, `data/`, `state/`, `cache/`, `tools/`, `backups/`, `roles.json`, `modes/`, `presets/`, `prompts/`. Сессии приложения — `data/sessions/`.

Плагин независимо читает `<home>/.canopus/plugin/config.json`. Регистрация OpenCode обычно содержит только пакет; выбор другого экземпляра — `options: {"config":"<absolute file>"}`. Настройки из регистрации в JSON не смешиваются. Тот же выбор действует в сервере, привязанном к нему TUI и MCP. У MCP и вспомогательных CLI есть `--config <file>`. Данные координации — `data/`, журнал и диагностика — `state/`, производные снимки — `cache/` **рядом с выбранным конфигом плагина**. Настройки, данные и аутентификация самого OpenCode остаются в OpenCode; XDG-каталоги OpenCode не меняют экземпляр Canopus.

Например, приложение с `--config C:/work/instances/demo/config.json` использует `C:/work/instances/demo/data/` и `C:/work/instances/demo/secrets.json`. Два файла **одной части** в одной папке делят данные. Приложение и плагин должны выбирать разные папки: внутренний маркер типа экземпляра блокирует смешивание. Один процесс не переключает экземпляр после загрузки ядра; для другого экземпляра нужен отдельный процесс.

`CANOPUS_HOME`, настройки через `CANOPUS_SERVER_*`, пользовательские таймеры окружения, `--home`, `--set`, `--file` и позиционный серверный JSON не являются входами конфигурации. При их обнаружении запуск завершается с понятной ошибкой без значений. Переменные ОС, аутентификация провайдеров и протокольный контекст агентов/сессий/наблюдений сохраняются; это не дополнительный слой настроек. Универсального `--port` тоже нет: изменяется `port` в выбранном файле.

## Публичные поля

Приложение принимает только:

| Поле | Назначение |
| --- | --- |
| `port` | Порт HTTP на loopback |
| `store` | Сохранённый выбор `files` или `pg` |
| `agents` | Список запускаемых ACP-агентов; их собственное окружение сохраняется |
| `voice.language` | Язык распознавания |
| `voice.model` | Имя файла модели в `tools/whisper/models/` |

`voice: false` отключает голос. Путь инструментов и фиксированный loopback-порт распознавателя вычисляются/задаются кодом. Аргумент модели относительный (`../models/...`) при рабочем каталоге `tools/whisper/bin`.

Плагин принимает одиннадцать проектных ключей: `tasks_dir`, `worktrees`, `model_profiles`, `profile_sets`, `profile_set`, `spawn_limits`, `inflight_limit`, `machine_slots`, `owner_language`, `answer_mode`, `acceptance_file`. Общий файл содержит только `project_settings`, `defaults`, `retention_days`. `project_settings` — массив каталогов репозиториев либо глобальных виртуальных определений `{project, root}`. Имена обычных проектов и принадлежность связанных рабочих деревьев выводятся из основного Git-дерева; старое имя remote не переименовывает проект.

Модели, выбранный профиль, лимиты запуска и машин, режим ответов сохраняются при переходе. `profile_set: false` — явное отключение набора; выбор через TUI записывается в проектный `.canopus/plugin/config.json` и действует без коммита. Снятые поля не образуют скрытый `advanced`: их именованные значения и прежние потребители остаются в реестрах кода `INTERNAL_POLICY`, `RUNTIME_POLICY`, `policy_keys()`. Фиксированы политика приёмки/ролей/форм плана/очистки и рабочие шаблоны; целевая ветка выводится из принятой ветки Git, пути установки и данных — из экземпляра/репозитория. Повторное открытие этих полей в будущем требует изменения публичного контракта.

## Приоритет файлов

Порядок от слабого к сильному: **встроенные значения → выбранный глобальный файл → проектный файл**. Более поздний слой перекрывает одноимённое значение предыдущего. Объекты объединяются по ключам, массивы заменяются целиком, `false`, `0` и пустая строка не пропадают.

Приложение: выбранный файл → `<repo>/.canopus/config.json`. Каталог экземпляра и стандартный глобальный `.canopus` не обнаруживаются как проектный слой. Секретные ключи читаются отдельно из соседнего `secrets.json`; обычные файлы их не принимают.

Плагин: глобальные `defaults` → `<repo>/.canopus/plugin/config.json` основной рабочей копии. Проектные значения сильнее глобальных. Рабочие деревья исполнителей не подменяют конфиг основного дерева. Обычные и виртуально зарегистрированные проекты читают и правят один и тот же проектный файл. Изменения действуют сразу, видны в Git diff, автокоммита нет. Битый файл блокирует чтение; сохранённый кеш настроек не является третьим источником.

Решение владельца, 2026-11-07, чат задачи 289: «два уровня конфигов — глобальный → проектный, без local.json и слоя local». Объект `local` глобального файла и проектные `local.json` удалены из схемы; при их обнаружении требуется явный переход. История запусков и снимки профилей остаются диагностикой, не подменяют действующий конфиг и не разрешают запуск по прежней модели при ошибке текущего набора.


## Секреты и PostgreSQL

Секреты провайдеров остаются в OpenCode. PostgreSQL обслуживает только приложение, не плагин и не MCP. Для backend `pg` соседний `secrets.json` содержит один `database_url` (postgresql/postgres URI); он не выводится в списке настроек. URI поддерживает процентное кодирование имени/пароля/БД, Unicode и IPv6; неподдерживаемые query/fragment отклоняются без печати URI. Инфраструктурные секреты управления PostgreSQL остаются в секции `postgres` и не превращаются в константы. Переход не меняет выбранный backend, БД, Docker или тома.

`.env` не является неявным источником Canopus. Не печатать значения секретов даже при ошибке устаревшего CLI-аргумента или переменной. Тестовые зависимости передаются явно через API; нового пользовательского environment override для тестов нет.

## Каталог задач и переход

`tasks_dir` — относительный каталог от корня проекта, по умолчанию `doc/tasks`; проект с документацией в `docs` может выбрать `docs/tasks`. Пустая строка использует каталог по умолчанию `doc/tasks` (288). Выход за корень запрещён. Каталог планов выводится из того же решения. Протокольные CLI-поля задания и подтверждения (`--session`, `--approval` и аналогичные) не меняют настройки экземпляра.

Переход схемы выполняется явно с предварительным отчётом и резервными копиями. Неэквивалентное снятое значение блокирует применение и требует решения; его нельзя молча потерять. Настоящие записи задач, письма, исходные ID и журналы не переписываются. Автоматическая удалённая очистка веток при миграции конфигурации запрещена. Старый перенос каталогов 285 (`scripts/migrate-canopus-layout.py`) остаётся отдельной явной операцией; постоянного чтения старых путей или junction нет.

Явный переход минимальной схемы: `python scripts/migrate-minimal-config.py --config <app-config> --plugin-config <plugin-config> --repo <installation-root>`. Без `--apply` только отчёт; `--apply` сохраняет резервные копии. Необязательный `--policy-root` позволяет проверить константы кандидата перед обновлением. Это переход формата полей предыдущей версии; затем выполняется переход двух уровней 289. Дополнительного указателя на репозиторий настроек нет.


## Каталог рабочих деревьев проекта

Владелец, 2026-11-07, чат интеграции: «Верни `worktrees` в настройки, чтобы можно было задавать каталог рабочих деревьев отдельно для каждого проекта, малый путь».

`worktrees` — публичная строковая настройка плагина. По умолчанию `../worktrees`; относительный путь разрешается от корня проекта, абсолютный используется напрямую. Например, `.canopus/plugin/config.json` может содержать `{"worktrees":"../project-trees"}`. Общее значение задаётся в `defaults.worktrees` глобального конфига, проектное — в `.canopus/plugin/config.json` соответствующего проекта. Действует обычный приоритет слоёв. Пустая строка оставляет автоматический каталог незаданным. Настройка влияет на новые деревья, существующие пути записей задач не перемещает. Старые имена файлов конфигурации не возвращаются.

## Единое хранилище задач (288)

Владелец, 2026-11-07, текущий чат: приложение Canopus и плагин используют одно место задач. Для проекта — `<project>/<tasks_dir>/`, по умолчанию `doc/tasks`; для задач без проекта — `~/.canopus/tasks/`. Каждая задача занимает `NNN-slug/`: задание, план, отчёты и журнал находятся рядом со служебной записью `task/state.json`. Состояние приватно и исключается из Git; документы в ветках — версионные снимки, не отдельные активные записи. Пустой прежний `tasks_dir` не отключает хранение состояния: используется `doc/tasks`.

Рабочие деревья используют каталог основного дерева проекта; номера резервируются под общей блокировкой. Исторические идентификаторы проектов и ссылки в задачах сохраняются. Служебный `state/task-projects.json` хранит обнаруженные привязки к корням для задач проектов вне текущего списка регистрации; это индекс размещения, не новый конфигурационный слой. Несколько имён одного корня читают один каталог, общая выдача не дублирует запись.

Подтверждения создания и отмены остаются обязанностью существующего жизненного цикла. Резервирование пустого каталога не создаёт задачу и не разрешает исполнение. Приложение сохраняет уже принятые движком события в ту же запись; общий путь и ограничения состояния читает из неё. Журнал сессии остаётся аудитом: при восстановлении события не применяются дважды. Незавершённая запись общего состояния блокирует исполнение. Пауза и execution HOLD/STOP не снимаются переносом.

Перенос выполняет `scripts/migrate-task-storage.py`: сначала отчёт без `--apply`, затем явное применение с проверенными резервными копиями. Различающиеся документы сохраняются в `imported-sources/` рядом с соответствующим документом; конфликт служебных записей блокирует перенос. Старое хранилище задач после проверки уходит в резервную копию, постоянного чтения старого пути нет. При повторном запуске проверяется квитанция переноса, операции задач и ответы не воспроизводятся.

Запись стража и HOLD хранится в `task/watch.json` той же задачи; перенос сохраняет её содержимое без повторного выполнения. Приватный `task/snapshot.json` учитывает подготовленные снимки документов. Перед штатным слиянием документы фиксируются в ветке задачи и подготавливаются для `ff-only`; посторонний индекс сохраняется, несовпадающие локальные версии блокируют операцию. Служебные записи и импортированные исходные варианты в снимок Git не попадают.

Приложение использует установленный дисковый адаптер `scripts/task-store.mjs` с Node.js 24 или новее. Адаптер не загружает хост плагина и не вызывает агентов; файл выбранного экземпляра определяет общее размещение обоих клиентов.

Общее размещение не передаёт полномочия между контроллерами исполнителей: задачу приложения плагин показывает, но не запускает и не останавливает через OpenCode. Для этих операций используется её окно приложения.

## Явный переход двух уровней (289)

`python scripts/migrate-two-level-config.py --config <app-config> --plugin-config <plugin-config> --report <report.json>` готовит отчёт без применения; `--apply` сохраняет проверенные оригиналы и применяет перенос. `--catalog` и повторяемый `--root` позволяют явно дополнить список проектов. Действующие настройки сравниваются до/после отдельно для приложения и плагина, включая отсутствие ключей, false, ноль и замену массивов. Исходные локальные изменения не теряются; конфликт действующих и незакоммиченных настроек блокирует применение.

Прежние личные слои сворачиваются в проектный файл. В глобальные значения выносятся только совпадающие настройки всех обнаруженных проектов: отсутствие настройки в одном проекте не разрешает добавлять её туда ради сокращения файла. Неактивные записи старого local сохраняются в резервной копии и явно отмечаются в отчёте. Повторное применение не меняет уже перенесённые файлы. При внешней записи применение прекращается, собственные изменения откатываются без перезаписи чужого изменения.

## Независимые ACP-семьи

Приложение запускает каждую запись `agents` её собственными `program` и `args` через ACP.
OpenCode — отдельная семья; Kimi, Codex, Claude и Z.ai не маршрутизируются через него.
Установленный `start.ps1` запускает приложение и один управляемый сборщик каталогов:
`initialize` и `session/new`, без `session/prompt`, инструментов клиента или файловых операций.
Каталог в `state/metadata/native-acp-catalog.json` живёт до четырёх минут и привязан
к точным идентификаторам, программам и аргументам настроенных семей. Ошибка одной семьи
не подменяет её моделями другой; устаревший каталог не используется.

Семья Z.ai использует отдельный процесс `scripts/zai-acp.mjs`: локальный Claude ACP-движок
обращается прямо к официальному API Z.ai. Ключ находится только в `zai.api_key` соседнего
`secrets.json`, окружение и кеш этой семьи изолированы от обычной семьи Claude.
Каталог предлагает GLM-модели, а не модели подписки Claude. Официальный транспорт:
[Z.ai для Claude Code](https://docs.z.ai/devpack/tool/claude).

Для семьи Kimi режим «Подготовка» использует закреплённый профиль `kimi-preparation.md` с единственным host-owned MCP `canopus_preparation`, без обычных инструментов, записи в проект и делегирования. MCP разрешает чтение и поиск в выбранном проекте, чтение публичного веба и проверяемые команды Git/поиска без оболочки и изменений. Каталог проекта и история чата назначаются сервером; пустая постановка не означает пустую историю. Ответ может изменить только назначенную постановку; обычный агент не используется как запасной путь. Модель и усилие подтверждаются через ACP, родная авторизация сохраняется.
