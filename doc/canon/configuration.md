# Конфигурация и данные Canopus

Решение владельца, 2026-11-06, чат задачи 285: единый пользовательский корень, независимые приложение и плагин, глобальные и проектные настройки, настраиваемый каталог задач. Ограничения в 30 минут для малого маршрута нет (прямое уточнение владельца в том же чате).

Корень — `CANOPUS_HOME`, по умолчанию `<home>/.canopus`; у приложения явно заданный `--home` сильнее окружения. Приложение читает `<root>/config.json` и отдельный `<root>/secrets.json`. Подкаталог `config/` не используется. `roles.json`, `modes/`, `presets/`, `prompts/` лежат в корне. Данные приложения — `data/`, сессии — `data/sessions/`, журналы — `state/`, производные данные — `cache/`, установки — `tools/`, резервные копии — `backups/`.

Плагин OpenCode и MCP используют `<root>/plugin/config.json`, данные координации — `plugin/data/`, диагностику и журнал веток — `plugin/state/`, снимок каталога моделей — `plugin/cache/`. Они не зависят от запущенного приложения или его PostgreSQL. Данные и аутентификация самого OpenCode остаются в OpenCode; изменение XDG-каталога OpenCode не меняет корень Canopus. Настройки приложения и плагина не смешиваются.

## Уровни

Низший приоритет — значения по умолчанию. Глобальный конфиг перекрывает defaults, проектный — глобальный, личный проектный — проектный, поддерживаемые переменные процесса — файлы, явно переданные аргументы — окружение. Отсутствующие ключи наследуются; объекты объединяются по ключам, массивы заменяются, false/0 не исчезают. Секреты приложения в secrets.json перекрывают обычные файлы только по секретным ключам; env и аргументы выше секретного файла. Значения секретов не печатаются.

Приложение: `<root>/config.json`, затем при явном указании серверный файл, `<repo>/.canopus/config.json`, `<repo>/.canopus/local.json`, `<root>/secrets.json`, env, CLI. Отдельный серверный файл сохраняется как явно выбранный источник до решения задачи 286.

Плагин: глобальные `defaults` из `<root>/plugin/config.json`, закоммиченные проектные настройки `<repo>/.canopus/plugin/config.json` из принятой целевой ветки, личные поправки из глобального `local[project]`, затем `<repo>/.canopus/plugin/local.json`, затем явно переданные опции запуска. Общий конфиг содержит `project_settings` (каталоги репозиториев настроек либо глобальные определения `{project, root}` с абсолютным корнем), `defaults` и необязательный `local`. Регистрация в OpenCode обычно содержит лишь пакет плагина; прежние машинные опции перенести в глобальный конфиг, не дублировать. Общий проектный конфиг остаётся принятым документом Git; личный local.json применяется без коммита и не попадает в Git. Плагин не получает автоматически все env-переменные приложения: у каждой части собственный поддерживаемый интерфейс.

Секреты провайдеров остаются в хранилище OpenCode. PostgreSQL обслуживает только приложение. Его инфраструктурные секреты хранятся в секции postgres файла secrets.json; пароль приложения — в pg.password. Не менять backend и не удалять том при переносе каталогов. Публичные настройки и их сокращение — отдельная задача 286; хаб в целевую архитектуру не входит, наличие команды его запуска отражает текущую реализацию.

## Каталог задач

`tasks_dir` в проектных настройках плагина — путь относительно корня репозитория; по умолчанию `doc/tasks`. В этом проекте используется `doc/tasks`. Проект с каталогом docs может задать `docs/tasks`. Пустая строка отключает папки задач. Выход за корень запрещён. CLI, плагин и страж документов используют этот параметр; явный CLI --tasks-dir переопределяет его. Рабочие деревья сохраняют принадлежность основному проекту.

## Перенос

`scripts/migrate-canopus-layout.py` по умолчанию лишь показывает источники и назначение; `--apply` явно копирует офлайн, проверяет SHA-256 каждого файла, защищает секреты и публикует новый каталог только после копирования. Существующий каталог назначения не перезаписывается. Источники сохраняются до проверки и отдельной уборки; никакого постоянного чтения старых путей или junction. Не переключать рабочие процессы на незавершённый перенос.

Имена проектов при явном переносе меняются только в структурированных полях и путях записей. Тексты писем, исходные ID сообщений и диагностические квитанции не переписываются. Коллизия записей останавливает перенос до публикации назначения.
