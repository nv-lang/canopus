# Конфигурация и данные Canopus

Решения владельца, чат задач 285–286, 2026-11-06: независимые приложение и плагин; обычный запуск без настроек; один явный выбор файла; пять публичных полей приложения и десять проектных полей плагина. Уточнение владельца: «согласен, но убранные настройки должны переехать в константы в коде, в будущем мы можем вернуться опять к варианту в настройках». Малый маршрут не ограничен временем.

## Выбор экземпляра

Приложение запускается командой `canopus` (равнозначно `canopus serve`). По умолчанию оно читает `<home>/.canopus/config.json`; `--config <file>` выбирает другой файл. Относительный CLI-путь разрешается от текущего каталога. **Родитель выбранного файла — корень экземпляра**: там лежат `secrets.json`, `data/`, `state/`, `cache/`, `tools/`, `backups/`, `roles.json`, `modes/`, `presets/`, `prompts/`. Сессии приложения — `data/sessions/`.

Плагин независимо читает `<home>/.canopus/plugin/config.json`. Регистрация OpenCode обычно содержит только пакет; выбор другого экземпляра — `options: {"config":"<absolute file>"}`. Настройки из регистрации в JSON не смешиваются. Тот же выбор действует в сервере, привязанном к нему TUI и MCP. У MCP и вспомогательных CLI есть `--config <file>`. Данные координации — `data/`, журнал и диагностика — `state/`, производные снимки — `cache/` **рядом с выбранным конфигом плагина**. Настройки, данные и аутентификация самого OpenCode остаются в OpenCode; XDG-каталоги OpenCode не меняют экземпляр Canopus.

Например, приложение с `--config C:/work/instances/demo/config.json` использует `C:/work/instances/demo/data/` и `C:/work/instances/demo/secrets.json`. Два файла **одной части** в одной папке делят данные. Приложение и плагин должны выбирать разные папки: внутренний маркер типа экземпляра блокирует смешивание. Один процесс не переключает экземпляр после загрузки ядра; для другого экземпляра нужен отдельный процесс.

`CANOPUS_HOME`, настройки через `CANOPUS_SERVER_*`, пользовательские таймеры окружения, `--home`, `--set`, `--file` и позиционный серверный JSON не являются входами конфигурации. При их обнаружении запуск завершается с понятной ошибкой без значений. Переменные ОС, аутентификация провайдеров и протокольный контекст агентов/сессий/наблюдений сохраняются; это не дополнительный слой настроек. Универсального `--port` тоже нет: изменяется `port` в выбранном файле.

## Публичные поля

Приложение принимает только:

| Поле | Назначение |
| --- | --- |
| `port` | Порт HTTP на loopback |
| `store` | Сохранённый выбор `files` или `pg` |
| `agents` | Список запускаемых ACP-агентов; их собственное окружение сохраняется |
| `voice.language` | Язык распознавания |
| `voice.model` | Имя файла модели в `tools/whisper/models/` |

`voice: false` отключает голос. Путь инструментов и фиксированный loopback-порт распознавателя вычисляются/задаются кодом. Аргумент модели относительный (`../models/...`) при рабочем каталоге `tools/whisper/bin`.

Плагин принимает десять проектных ключей: `tasks_dir`, `model_profiles`, `profile_sets`, `profile_set`, `spawn_limits`, `inflight_limit`, `machine_slots`, `owner_language`, `answer_mode`, `acceptance_file`. Общий файл содержит только `project_settings`, `defaults`, `local`, `retention_days`. `project_settings` — массив каталогов репозиториев либо глобальных виртуальных определений `{project, root}`. Имена обычных проектов и принадлежность связанных рабочих деревьев выводятся из основного Git-дерева; старое имя remote не переименовывает проект.

Модели, выбранный профиль, лимиты запуска и машин, режим ответов сохраняются при переходе. `profile_set: false` — явное личное отключение набора; выбор через TUI записывается в проектный `local.json`, каталог моделей и наборов остаётся общим документом. Снятые поля не образуют скрытый `advanced`: их именованные значения и прежние потребители остаются в реестрах кода `INTERNAL_POLICY`, `RUNTIME_POLICY`, `policy_keys()`. Фиксированы политика приёмки/ролей/форм плана/очистки и рабочие шаблоны; целевая ветка выводится из принятой ветки Git, пути установки и данных — из экземпляра/репозитория. Повторное открытие этих полей в будущем требует изменения публичного контракта.

## Приоритет файлов

Порядок от слабого к сильному: **встроенные значения → выбранный глобальный файл → проектный файл → личный проектный файл**. Более поздний слой перекрывает одноимённое значение предыдущего. Объекты объединяются по ключам, массивы заменяются целиком, `false`, `0` и пустая строка не пропадают.

Приложение: выбранный файл → `<repo>/.canopus/config.json` → `<repo>/.canopus/local.json`. Каталог экземпляра и стандартный глобальный `.canopus` не обнаруживаются как проектный слой. Секретные ключи читаются отдельно из соседнего `secrets.json`; обычные файлы их не принимают.

Плагин: глобальные `defaults` → закоммиченный `<repo>/.canopus/plugin/config.json` из принятой ветки основного дерева → глобальный `local[project]` → `<repo>/.canopus/plugin/local.json`. Глобальные виртуальные определения и личные поправки других проектов сохраняются без записи в их репозитории. Производные снимки проектов и старый кеш настроек не заменяют авторитетный конфиг. Регистрация OpenCode выбирает файл, а не вводит верхний слой значений.

## Секреты и PostgreSQL

Секреты провайдеров остаются в OpenCode. PostgreSQL обслуживает только приложение, не плагин и не MCP. Для backend `pg` соседний `secrets.json` содержит один `database_url` (postgresql/postgres URI); он не выводится в списке настроек. URI поддерживает процентное кодирование имени/пароля/БД, Unicode и IPv6; неподдерживаемые query/fragment отклоняются без печати URI. Инфраструктурные секреты управления PostgreSQL остаются в секции `postgres` и не превращаются в константы. Переход не меняет выбранный backend, БД, Docker или тома.

`.env` не является неявным источником Canopus. Не печатать значения секретов даже при ошибке устаревшего CLI-аргумента или переменной. Тестовые зависимости передаются явно через API; нового пользовательского environment override для тестов нет.

## Каталог задач и переход

`tasks_dir` — относительный каталог от корня проекта, по умолчанию `doc/tasks`; проект с документацией в `docs` может выбрать `docs/tasks`. Пустая строка отключает папки задач. Выход за корень запрещён. Каталог планов выводится из того же решения. Протокольные CLI-поля задания и подтверждения (`--session`, `--approval` и аналогичные) не меняют настройки экземпляра.

Переход схемы выполняется явно с предварительным отчётом и резервными копиями. Неэквивалентное снятое значение блокирует применение и требует решения; его нельзя молча потерять. Настоящие записи задач, письма, исходные ID и журналы не переписываются. Автоматическая удалённая очистка веток при миграции конфигурации запрещена. Старый перенос каталогов 285 (`scripts/migrate-canopus-layout.py`) остаётся отдельной явной операцией; постоянного чтения старых путей или junction нет.

Явный переход минимальной схемы: `python scripts/migrate-minimal-config.py --config <app-config> --plugin-config <plugin-config> --repo <installation-root>`. Без `--apply` только отчёт; `--apply` сохраняет резервные копии. Необязательный `--policy-root` позволяет проверить константы кандидата перед обновлением. У виртуальных проектов каталог профилей и наборов записывается в глобальный `local[project]`, личный выбор профиля — в `.canopus/plugin/local.json` корня виртуального проекта. Дополнительного указателя на репозиторий настроек нет.
