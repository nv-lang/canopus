# Как Codex работает с целями: постановка, шаги, критерий приёмки, автозапуск (исследование 2026-11-21)

Раздел «что перенести» отобран по критериям [doc/research/README.md](README.md).

Повод: владелец спросил, как устроены «цели» в Codex и что из этого стоит перенести в Канопус.
Источник — открытый репозиторий `openai/codex`, клон разбора 300, ревизия **`4360c5f8133632a5655fd28a5e33828c9b76056c`**
(Rust, `codex-rs/`). Всё ниже — чтение исходников, без запуска.

Обозначения: **[V]** — проверено по коду (путь:строка); **[I]** — вывод.

## Главное

- У Codex есть **полноценная подсистема целей** отдельным расширением `codex-rs/ext/goal/` (~3,4 тыс. строк):
  сервис, рантайм, учёт токенов/времени, стеering-промпты, аналитика, метрики. **[V]**
- Цель = `objective` (одна строка, до 4000 символов) + статус + необязательный **token_budget**. Отдельного поля
  «критерий приёмки» нет — приёмка задана **текстом контракта продолжения** и аудитом завершения. **[V]**
- Исполнение держат: автопродолжение по простою потока, учёт расхода токенов/времени, авто-остановки по сбоям и
  лимитам, промпты «проверь доказательства, а не намерения». **[V]**
- Резюме, продление, бюджеты и usage-лимиты меняет **только пользователь/система**; модель может лишь
  `complete` / `blocked` / паузу по явной просьбе. **[V]**

## 1. Когда ставится цель

- Инструменты (только у основного агента; у Review-подагентов скрыты): `create_goal`, `update_goal`, `get_goal`
  (`codex-rs/ext/goal/src/spec.rs:12-14`). Схема `create_goal`: `objective` (обязателен) + `token_budget`
  («omit unless explicitly requested») — `spec.rs:32-60`. **[V]**
- Политика в описании инструмента: «Create a goal only when explicitly requested by the user or system/developer
  instructions; do not infer goals from ordinary tasks»; при незавершённой цели создание падает
  («complete the existing goal first»), `update_goal` для статуса — `spec.rs:47-60`, `tool.rs:230-238`. **[V]**
- `update_goal` принимает только `complete | blocked | paused` (`spec.rs:63-77`); паузу — только по явной просьбе
  пользователя; резюм/бюджет/usage-лимиты моделью недоступны (`tool.rs:270-280`). **[V]**
- Пользовательская сторона — отдельный API (`GoalService::set_thread_goal`, `api.rs:147-160`): объектив + статус;
  цель по умолчанию — `active`. Изменения от пользователя подаются модели как **отдельный контекст** с
  происхождением (`core/src/context/user_goal.rs`): «Never construct this from tool output or an automatic
  continuation»; объективы >700 байт в контекст **не вставляются вовсе** (чтобы урезание не превратило
  ограничение в разрешение) — `user_goal.rs:1-22,66-78`. **[V]**
- Статусы: `active, paused, blocked, usage_limited, budget_limited, complete` (`protocol.rs:4558-4568`);
  объектив ≤4000 символов (`protocol.rs:4570-4581`). **[V]**

## 2. Как строятся шаги и «план»

- Рантайм-плана у цели нет. Есть отдельный инструмент `update_plan` — это todo/чеклист, **не** обновление
  plan-режима (`app-server/src/bespoke_event_handling.rs:1395`); он может быть выключен конфигом
  (`update_plan_enabled`, `core/src/config/mod.rs:1185`). **[V]**
- Шаги держит текст контракта продолжения (`ext/goal/templates/goals/continuation.md`): «цель живёт через ходы»,
  «держись полного объектива, не сужай удачу по тому, что влезает сейчас», «оптимизируй ход на движение к
  конечному состоянию, а не на минимальный зелёный кусок». Если `update_plan` доступен и работа реально
  многошаговая — «покажи краткий план, привязанный к объективу, держи его актуальным», но «обновление плана — не
  замена работе». **[V]**
- В плановом режиме (`ModeKind::Plan`) токены хода в бюджет цели не засчитываются (`accounting.rs:92-108`). **[V]**
- Продолжение приходит шаблоном с текущими числами: `tokens_used / token_budget / remaining_tokens`
  (`steering.rs:87-110`), а сам объектив передаётся как **недоверенный** дополнительный контекст
  (`AdditionalContextKind::Untrusted`, `steering.rs:66-76`). **[V]**

## 3. Критерии приёмки

- Хранимого критерия нет; вместо этого контракт продолжения задаёт **аудит завершения** (`continuation.md`,
  раздел «Completion audit»): вывести конкретные требования из объектива и всех упомянутых файлов/планов/спецификаций;
  не переопределять успех под уже сделанное; для каждого требования найти **авторитетное свидетельство**
  (файлы, вывод команд, тесты, PR, артефакты, поведение) и сверить масштаб проверки с масштабом требования;
  «слабое/косвенное свидетельство считать невыполнением»; «аудит должен **доказать** завершение, а не merely
  не найти очевидной работы». **[V]**
- Отдельно: «No-progress check» — классифицировать прошлый ход как прогресс / проверенное ожидание / отсутствие
  прогресса; «ожидание подтверждено только живым сейчас процессом/сессией/джобом; таймаут наблюдения — не
  терминальное состояние; не перезапускай только из-за истечения наблюдения». **[V]**
- `update_goal(complete)` возвращает учёт расхода, чтобы итог сохранился; для цели с бюджетом модель обязана
  сообщить пользователю финальный расход после успеха (`spec.rs:70-77`, `tool.rs:360-395`). **[V]**
- Правило блокировки: `blocked` — только после **трёх подряд** ходов цели с тем же блокером; после резюма аудит
  начинается заново; «не блокировать из-за сложности/объёма/неполноты» (`spec.rs:63-77`, `continuation.md`). **[V]**

## 4. Как обеспечивается автозапуск

- Триггер — **простой потока**: `ThreadLifecycleContributor::on_thread_idle` → `continue_if_idle`
  (`extension.rs:181-205`, `runtime.rs:433-525`). Условия: цель `active`, расширение доступно, есть живой поток,
  нет `thread_goal_continuation_deferral`; запуск — `start_turn_if_idle` с `turn_trigger: "goal"`, чтобы запись
  учёта не путалась с пользовательским ходом; при отказе — молча пропустить (`runtime.rs:483-515`). **[V]**
- Учёт: токены хода = не-кэшированный вход + выход (`accounting.rs:570-577`), плюс время и токены подагентов
  (`descendant_token_usage`); автоматический ход помечается (`mark_goal_continuation`). **[V]**
- **Авто-остановки** (статус меняет рантайм, не модель) — `runtime.rs:260-400`:
  - ошибка хода (`TurnError`) → `blocked`;
  - исчерпан лимит провайдера (`UsageLimit`) → `usage_limited` (может заменить `budget_limited`);
  - **три подряд** хода с провалившимся исполнением и без успешных инструментов
    (`consecutive_execution_failure_turns >= 3`, `accounting.rs:140-174`) → `blocked`;
  - **автоматический** ход без активности и с пустым финалом/прерыванием (`EmptyResponse`, `accounting.rs:229-240`)
    → `blocked` — защита от пустых циклов. **[V]**
- **Бюджет токенов**: только токены (бюджетов ходов/времени нет). Конфиг `[goals] max_goal_token_budget` —
  одновременно максимум и бюджет по умолчанию для новых целей (`core/src/config/mod.rs:1038`, `tool.rs:219-220,
  447-460`). При пересечении рантайм ставит `budget_limited` и вставляет steering-промпт
  (`templates/goals/budget_limit.md`): «не начинай новую содержательную работу, сверни ход: прогресс, остаток,
  следующий шаг»; «`budget_limited` важнее `paused`» (`extension.rs:540-552`). **[V]**
- Редактирование объектива пользователем — отдельный steering-промпт «новый объектив заменяет прежний, не
  продолжай работу, которая служила только старому» (`templates/goals/objective_updated.md`). **[V]**

## 5. Хранение и жизненный цикл

- Цель хранится в **state DB** (`codex_state::GoalStore`, `state/src/runtime.rs:108,313`) и публикуется в rollout
  событием `ThreadGoalUpdatedEvent {thread_id, turn_id?, goal}` (`protocol.rs:4600-4608`); на резюме потока
  активная цель восстанавливается (`runtime.rs:415-430`). **[V]**
- Форк: перед копированием снимка цели выполняется `flush_thread_goal_progress_for_fork` — учёт доводится до
  границы, чтобы форк получил согласованный снимок (`api.rs:112-129`). **[V]**
- Цель принадлежит потоку (thread), у каждого потока — одна цель. Очередь целей не обнаружена; `ThreadQueueChangedEvent`
  относится к очереди ходов. **[I]**

## 6. Что стоит перенести в Канопус (идеи)

1. **Раздельные терминальные статусы**: `usage_limited` и `budget_limited` отдельно от `blocked`/`paused` — у нас
   сейчас такого различия нет; это честная причина остановки в UI и в журнале. **[I]**
2. **Промпт «бюджет исчерпан — сверни, не начинай»** отдельным сообщением, с приоритетом над паузой — хорошо
   ложится на наши ворота и на «малый путь». **[I]**
3. **Рантайм-детекция тупика, а не только самооценка модели**: три подряд провала исполнения без успешных
   инструментов → `blocked`; пустой автоматический ход → `blocked`. Это прямой антидот от «кругов по одному и
   тому же». **[I]**
4. **Контракт продолжения как текст**: «no-progress / verified wait» с правилом «таймаут наблюдения — не
   терминальное состояние; не перезапускай только из-за истечения наблюдения» — ровно наш класс 317/320. **[I]**
5. **Аудит завершения по требованиям со свидетельствами** и «слабое доказательство = не сделано» — усилить этим
   формулировки наших ворот приёмки. **[I]**
6. **Объектив как недоверенный контекст** и «слишком длинный объектив не вставлять вовсе» (антипаттерн урезания) —
   применимо к нашим напоминаниям о задаче. **[I]**
7. **Права**: резюм/бюджет/usage меняет только пользователь/система; модель — только complete/blocked/paused по
   просьбе. Совпадает с жизненным циклом задач Канопуса — стоит зафиксировать явно. **[I]**
8. **Форк**: довести учёт до границы перед снимком цели (у нас — передача контекста 298). **[I]**

## 7. Отличия от Kimi Code (см. соседнее исследование)

- У Codex нет хранимого `completionCriterion` — приёмка живёт в тексте контракта продолжения; у Kimi — отдельное
  поле. **[I]**
- Бюджеты Codex — только токены (turns/time нет); у Kimi — turns/tokens/время. **[V/I]**
- Очередь целей и авто-подъём следующей — есть у Kimi, у Codex не найдено. **[I]**
- Оба: продолжение отдельным системным триггером, блокировка после 3 ходов, «слабое доказательство ≠ done»,
  объектив как недоверенные данные, пауза/резюм только пользователем. **[V]**
