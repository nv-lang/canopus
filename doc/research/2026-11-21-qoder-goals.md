# Как Qoder работает с целями: постановка, шаги, критерий приёмки, автозапуск (исследование 2026-11-21)

Раздел «что перенести» отобран по критериям [doc/research/README.md](README.md).

Повод: владелец спросил, как устроены «цели» в Qoder и что из этого стоит перенести в Канопус.
Источник — **установленное приложение Qoder** (десктоп, версия приложения **0.5.6**): содержимое `app.asar`
распаковано в память и прочитано (`out/main/chunks/*.js`, `out/main/electronMain.js`,
`out/renderer/assets/{2NXLGhal,DidgxRds,4YlEfiER}.js`). Код минифицирован и обфусцирован, но схемы IPC,
тексты интерфейса и модели данных читаемы. Агентское ядро и промпты живут на стороне сервиса и в асар не входят.
Пометки: **[V]** — проверено по коду/строкам установленного приложения; **[I]** — вывод.

## Главное

- У Qoder есть **Goal mode** («Goal-driven execution», «目标驱动执行»): пользователь включает режим и задаёт цель;
  Qoder **сам продолжает ходы до достижения цели или исчерпания лимита** (`settings.goalMaxTurnsDescription`). **[V]**
- Цель — объект сессии: `{id, objective, status, turnsUsed, maxTurns, creditsBudget, creditsUsed,
  activeElapsedMs, lastResumedAt, createdAt, updatedAt}`. Статусы: `active, completed, paused, blocked,
  budgetLimited, usageLimited`. **[V]**
- Критерий приёмки — часть **текста цели**: редактор цели прямо просит «goal, constraints, acceptance criteria».
  Отдельного verify-шага в десктопе нет — завершение отмечает агент (tool-контракт create_goal/update_goal
  приходит с сервиса). **[V/I]**
- План — отдельный режим (**Plan**) и «спека» (Plan artifact) с версиями и согласованием; из плана можно
  **стартовать цель**: «Execute this plan in Goal mode — keep working toward the goal and adjust the next steps». **[V]**

## 1. Когда ставится цель

- Пользователь: режим **Goal** в композере (переключатель `toggle-goal-mode`, подпись «Goal» / «目标»; поддержан и
  ввод `/goal …` — парсер `^/goal(?:\s|$)`); сама цель создаётся через `chatSessions.setGoal {sessionId, objective}`,
  максимум назван «goalMaxTurns» (лимит по цели, схема `{min:1,max:N}`). **[V]**
- Режимы независимы: `goalModeSelected` и `planModeSelected` — разные поля сессии; включение цели не включает план. **[V]**
- Из плана: после согласования плана у пользователя есть выбор «Execute this plan in Goal mode» (диалог отправляет
  `{approved:true, startGoal:true}`) — план становится стартовым маршрутом цели; «продолжай идти к цели, поправляй
  следующие шаги по результатам». **[V]**
- Действия над целью в UI: редактировать, поставить на паузу, продолжить, удалить («Edit goal», «Pause goal»,
  «Resume goal», «Delete goal», «Usage-limited goal», «Budget-limited goal»); API:
  `getGoal / setGoal / resumeGoal / clearGoal / setGoalMaxTurns` (контрольные операции). **[V]**
- Одна цель на сессию; поля `turnsUsed/maxTurns`, `creditsBudget/creditsUsed` — бюджеты цели. **[V]**
- Ограничение места: в Live voice режим цели недоступен («Goal mode isn't available in Live voice tasks»). **[V]**

## 2. Шаги и «план»

- Внутри цели нет структуры шагов: цель — текст (objective) с ограничениями и критериями приёмки; агент сам решает
  следующий шаг, а рантайм продолжает ходы. **[V/I]**
- План — отдельный режим Plan и **Plan artifact** («计划», «Plan»): документ с версиями и статусами
  `pending / approved / accepted`, правками и обратной связью; виден в «Task monitor» рядом с целью и generated files. **[V]**
- Task monitor: «goal», `specArtifact`, сгенерированные файлы, «recap» (короткий обзор задачи) — панель наблюдения,
  не источник истины. **[V]**
- Рядом (не цели): **Issue** в коллаборации несёт отдельное поле `successCriteria` («验收标准», «verifiable
  outcome») — приёмка на уровне задачи-issue, и **Quest mode** — командный режим (лидер/участники, acceptance по
  взаимодействию). С целью они не смешиваются. **[V]**

## 3. Критерий приёмки

- В редакторе цели: «Clearly describe the goal, constraints, and acceptance criteria» — критерии пишет человек
  в тексте цели. **[V]**
- Завершение: статус `completed` (UI «Completed goal»), рядом — `blocked`, `budgetLimited`, `usageLimited`;
  переходы делает агентский контракт `create_goal/update_goal` на стороне сервиса (в приложении есть только имена
  инструментов и индикаторы; правило «блок — после повторов» — из сервисного контракта). **[V/I]**
- Автоматического отдельного «судьи» (как evaluator у Claude Code/ZCode) в десктопе не найдено; проверка —
  агентская. **[V — не найдено; I — вывод]**
- `creditsUsed` у цели даёт видимую стоимость; `creditBudget` — лимит по кредитам. **[V]**

## 4. Автовыполнение

- Настройка `Goal-driven execution`: «After you set a goal, Qoder continues automatically until the goal is achieved
  or the budget is exhausted»; `goalMaxTurns` — максимум ходов на цель, задаётся в настройках и на сессию. **[V]**
- Учёт: `turnsUsed/maxTurns` (ходы), `creditsUsed/creditsBudget` (кредиты), `activeElapsedMs` + `lastResumedAt`
  (время активной работы; пауза фиксирует, продолжение открывает новый интервал) — те же поля, что в UI строки
  цели «Running for {{duration}}». **[V]**
- Пауза/продолжение — явные операции (`goalAction: pause|resume`, `resumeGoal`), не «просто новый prompt»;
  `blocked/budgetLimited/usageLimited` — отдельные статусы остановки, а не «ошибка». **[V]**
- Перезапуск/резюме: цель хранится как объект сессии и восстанавливается вместе с ней (`getGoal` возвращает
  текущую цель после переподключения). **[V]**
- Первый запуск подсвечен «first use sticker» — продукт объясняет режим на старте. **[V]**

## 5. Что стоит перенести в Канопус (идеи)

1. **Два отдельных режима композера — Plan и Goal** и явная связка «одобрил план — выполнить его в режиме цели,
   поправляя шаги по результатам». У нас ворота принятия плана и постановка цели разнесены; связка удобна. **[I]**
2. **Turn- и credit-бюджеты на цель** (`turnsUsed/maxTurns`, `creditsUsed/creditsBudget`) как видимые поля рядом с
   целью; лимит по ходам — настройкой «goal-driven execution». **[I]**
3. **`activeElapsedMs`/`lastResumedAt`**: пауза фиксирует интервал, продолжение открывает новый — простой и
   переносимый учёт времени (сравнимо с `usage_limit_waiting` у Claude Code). **[I]**
4. **Статусы `blocked / budgetLimited / usageLimited` отдельными состояниями** с иконками и текстами — разговор с
   владельцем «почему остановились» становится однозначным. **[I]**
5. **Редактирование текста цели** (objective + constraints + acceptance criteria) прямо в UI с сохранением истории
   — критерий приёмки живёт рядом с целью, а не в отдельном документе. **[I]**
6. **Task monitor (цель + спека + файлы + recap)** как панель прогресса; спека — версии и статусы согласования. **[I]**
7. **Явные pause/resume/clear** и хранение цели в сессии (восстановление при переподключении). **[I]**

## 6. Отличия от Kimi Code, Codex, ZCode, Claude Code

- Qoder: автопродолжение привязано к **лимиту ходов** и кредитам цели; отдельного evaluator’а в приложении нет —
  завершение определяет агент; приёмка — текст цели. **[V/I]**
- ZCode и Claude Code: отдельный автоматический судья (verifier/evaluator) с JSON-вердиктом; Codex — только
  токен-бюджет и рантайм-детекция тупиков; Kimi — бюджет turns/tokens/время и аудит в тексте. **[I]**
- У всех — автопродолжение отдельными ходами, objective как пользовательские данные, пауза/продолжение по слову
  пользователя; у Qoder дополнительно — режим Plan с передачей в Goal и панель Task monitor. **[V/I]**

## Ограничения исследования

- Приложение минифицировано/обфусцировано (строки через массив-индирекцию); агентское ядро, промпты и правила
  создания/завершения цели — на серверной стороне и в асар не входят, поэтому внутренние формулировки
  (например, «блок после трёх повторов») восстановлены как **[I]** по контракту инструментов, а не по коду. **[I]**
- Версия зафиксирована по `package.json` внутри асар (`0.5.6`); в свежих сборках поля могли измениться. **[V]**
- Раздел Quest (командный режим) намеренно не разбирался — это не цели; матрица его acceptance относится к
  взаимодействиям команды. **[I]**
