# Задание: Изолировать блокировку одного вопроса в router

Заказчик: canopus.integrator; задание собрано плагином из полей canopus_spawn.
Репозиторий: проект canopus, ветка main. Дата задания: 2026-11-11.
Источник: слова владельца с датой — раздел «Чего хочет владелец».

## Чего хочет владелец

«Исправить отдельно (Recommended)» (владелец, 2026-11-11, текущий чат, прямой ответ question «Разблокировать router»: разрешена отдельная задача изолировать ошибку исторического lock, чтобы остальные вопросы, включая следующий шаг 290, получали адресата и эпоху; исторический lock/blocker сохранить, повторные native POST запретить, scope 290/136 не расширять, live отдельно).

## Что нужно

1. Исправить подтверждённый отказ общего прохода question router: исключение [locked] для исторической записи не должно прерывать обработку остальных независимых вопросов. В question-router.ts tick обходит все записи; change использует fail-closed lock-каталог, а исключение одной записи сейчас прерывает проход. Новые рабочие вопросы остаются routing с epoch 0 без target. Сохранить исторический lock и его явный blocker, не признавать его просроченным по возрасту и не присваивать чужую блокировку. Изолировать только отказ одной записи, позволив остальным пройти существующие проверки источника, адресата, scope, HOLD и native outcome. Работа в отдельном worktree от origin/main; код основной копии не менять.

## Критерии приёмки

1. Детерминированный RED→GREEN: первая историческая запись имеет существующий lock, последующая независимая получает актуальный target, ненулевую epoch и маршрутное письмо; отдельный валидный готовый ответ проходит свой штатный путь. 2. Заблокированная запись, lock, прежние question/qid/context/ответы и исходный native outcome не переписаны/не удалены; наблюдаемый blocker остаётся. 3. Несколько вопросов и проекты: ошибка одного не лишает остальные обработки; нет дублированных route/answer/native POST при повторе tick, рестарте и конкуренции. Unknown/applied/owner gates и HOLD не превращаются в разрешение. 4. Изоляция ошибки типизированная и узкая: не скрывать произвольную порчу записи/схемы или транспортные ошибки как успешный проход; результат и локальный отказ диагностируемы. 5. Тесты источника/scope/смены ответственного/epoch/owner precedence/unknown outcome не регрессируют. Targeted RED/GREEN, полный набор плагина включая pretest и стражи через queue с проверенным cwd/HEAD/exit без tail; падения параллельного запуска перепроверяются отдельно, никакой RED не объявлять GREEN. 6. Signed exact SHA, независимая приёмка и отчёт с проверяемыми raw. Применение в live и обновление main отдельно только по слову владельца; OpenCode не перезапускать. После принятия указать, как безопасно дать существующему вопросу 290 штатно назначиться, без нового qid/ручной epoch.

## Результат и куда он попадает

Код question router opencode-plugin/question-router.ts и узкие вызывающие адаптеры при необходимости; регрессионные тесты и актуальная документация. Независимо принятый exact SHA и безопасный путь активации, без автоматической правки live.

## Связи

Блокирует: существующий рабочий маршрут Canopus 290 «Разделить SHA документов и результата при межрепозиторном слиянии». Пересекается: принятая 280 «Рабочие вопросы через интегратора» (router), 281 (координация). Не является расширением 136 или 290.

## Границы

Только per-record отказ lock и необходимая наблюдаемость/тесты/документация. Не удалять/переименовывать lock, не редактировать runtime JSON/role/epoch/статусы, не отправлять повторный native POST/prompt. Не чинить classifier package-release.ps1, source/report lifecycle, health recovery или 136/290: это отдельные находки, scope не расширять. Не править другие репозитории. Не push/main/live/service до полного GREEN и отдельно разрешённой интеграции/активации. В публичные файлы не переносить реальные runtime IDs, пути машины и секреты; сценарии на изолированных fixtures.
