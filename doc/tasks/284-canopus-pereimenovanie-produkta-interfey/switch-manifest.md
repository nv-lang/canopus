# Switch-манифест задачи 284: CrewHarness → Canopus

Закрытый перечень действий переключения. Выполняется ТОЛЬКО после отдельного owner gate: кандидат заморожен
(exact SHA зафиксирован), полный npm-набор (включая pretest) и Nova-набор зелёные, владелец сказал «обновляй»,
основная копия обновлена оркестратором, службу останавливает и запускает владелец (п. 12 AGENTS.md).
Никаких переходных периодов: после переключения старые имена не читаются нигде.

## Порядок

1. **Стоп службы** — владелец: `powershell -File scripts/stop-opencode.ps1` из основной копии (печатает `0`,
   когда процессов не осталось). Папку ящика после этого никто не держит (п. 13).
2. **Ящик плагина** — из основной копии `opencode-plugin/`: `node migrate-mailbox.mjs`.
   Ожидаемая квитанция на машине владельца: `migrated: <…>/crew-harness, <…>/opencode-peers, <…>/nova-peers ->
   <…>/canopus` — ссылки-junction сняты, настоящая папка (nova-peers, живые данные) переименована.
   Переносить нечего (уже перенесено / новая установка) — печатает `nothing to migrate`.
   Отказ («несколько настоящих прежних ящиков», «ссылка наружу», «новый уже есть, а прежний остался») — СТОП,
   ручной разбор, откат ниже.
   Откат: `node migrate-mailbox.mjs --rollback` (возвращает `canopus` в `crew-harness`).
   Проверка: рядом с `canopus` не осталось ни одного прежнего имени (ни папки, ни junction).
3. **Конфиг Canopus** — если существует `~/.config/crew-harness/` (home слоя конфигов: config.json, secrets.json,
   pg.json, prompts/): переименовать в `~/.config/canopus/`. Переменные окружения `CREW_*`/`OPENCODE_CREW_*`,
   если где-то прописаны (пусковые файлы, реестр env): переименовать в `CANOPUS_*`/`OPENCODE_CANOPUS_*` —
   иначе отказ при старте (так задумано, без fallback).
4. **MCP-сервер** — в конфиге OpenCode владельца регистрация сервера под прежним именем переименовывается в
   `canopus` (команда та же — `node opencode-plugin/mcp.ts`; serverInfo уже `canopus`). Старые вызовы
   `mcp__crew__*` не исполняются: подсказка даёт новое имя.
5. **Prompt-файлы** — если владелец заводил свои тексты в `.canopus/prompts/` проекта или
   `<home>/config/prompts/`: файлы `tool_crew_*.md` переименовать в `tool_canopus_*.md` (имена следуют
   текущим именам инструментов; неизвестные файлы просто не читаются — встроенный текст остаётся).
6. **PostgreSQL-контур (если используется — уточнить у владельца; если нет, пункт пропускается):**
   контейнер `docker rename crew-harness-pg canopus-pg`; база, схема и роль внутри:
   `ALTER DATABASE crew RENAME TO canopus;` (без активных подключений), `ALTER SCHEMA crew RENAME TO canopus;`,
   `ALTER ROLE crew_service RENAME TO canopus_service;`. Том Docker не переименовывается: либо оставить имя
   `crew-harness-pg-data` и поправить `db.ps1` отдельной правкой, либо backup (`db.ps1 backup`) → новый `up` →
   `restore`. Конфиг подключения `~/.config/canopus/pg.json` уже перенесён шагом 3.
7. **Браузерные ключи** — localStorage `/^crew-/` инертны: читаются только ключи `/^canopus-/`. Старые ключи
   можно не трогать (потеря — только локальные UI-настройки вкладок) или удалить вручную.
8. **Старт** — владелец запускает окна проектов их скриптами (первое окно поднимает службу). После перезапуска
   владелец пишет «перезапустил»; оркестратор проверяет журнал плагина и `canopus_doctor`.
9. **Проверка после старта** — `canopus_doctor` зелёный; письмо проверки связи доходит; `canopus_task list`
   отвечает; веб-морда открывается (boot-guard принимает ключи `canopus-*`).

## Что манифест НЕ делает

- Не трёт и не переписывает историю: doc/tasks, doc/archive, doc/research, цитаты владельца, подписанные
  evidence — сохраняются как есть.
- Не меняет форматы: machine/2, test/0, версии протоколов, session/task/qid/reply_to/receipts.
- Не создаёт алиасов: ни junction, ни двойного чтения старых env, ни fallback на старое имя.
