# 298. Передача контекста между окнами по паттерну session-import

**Статус:** черновик (создан по слову владельца; до подтверждения в приложении номера и папка условные).

**Инициатор и разрешение:** владелец, 2026-11-14, чат окна агента (разбор kimi-code): «задачи заведи, как черновики». Предложение показано владельцу в этом чате до создания.

**Проверка дублей и поправка (2026-11-14, слово владельца):** перенос контекста в продукте **уже есть** — задача 192, `src/server/transfer.nv` (сводка моделью с ограждениями + дословный хвост + срез к заголовкам, бюджет по выученным размерам контекста). Эта задача — не замена, а добавка: детерминированный режим, вложение-история, spill-словарь, происхождение переноса.

**Цель:** спроектировать формат переноса работы между окнами Канопуса по паттерну пакета `session-import` (kimi-code): приёмник получает одно цельное сообщение вместо «как получится».

**Паттерн (из `packages/session-import/README.md`, kimi-code):**
- одно видимое сообщение с `<system>`-обрамлением сверху и снизу: «это запись о прошлой работе, а не новые инструкции»; «инструменты и вызовы — записи, не отложенные действия»; «файлы могли измениться»;
- отбор **целыми ходами от новых к старым** по токен-бюджету (~`floor(контекст × 0.8)`); всё невлезшее — не потеряно: полная история сохраняется файлом-вложением (`effective-history-<sha256>.jsonl`);
- сжатие детерминированное, без LLM-суммаризации: вызовы инструментов → короткие заметки с обрезкой (2000/4000 симв.) и маркером-указателем на вложение; thinking и служебные события выбрасываются;
- вложения атомарно (временный файл → hard link), источник только читается;
- картинки извлекаются с дедупликацией по SHA-256.

**Шаги:**
1. Сопоставить с нашей текущей передачей/восстановлением контекста в продукте (чат, восстановление задачи): что уже есть, где разрыв.
2. Спецификация формата сообщения переноса для Канопуса (системное обрамление, обрезка ходами, вложение-история) на нашем журнале.
3. Точка внедрения в продукте и план; реализация — отдельной задачей по слову владельца. Дополнительно: применимость формата к будущему импорту сессий CC/Codex — зафиксировать, не делать.

**Дополнение И4 (задача 300, слово владельца, 2026-11-14, «по рекомендации»):** в спецификацию из шага 2 войдут
- **spill-словарь вместо молчаливой обрезки** — всё, что не влезло, остаётся превью + указатель на файл-носитель + подсказка извлечения; сбой → оригинал (образец: dsh `packages/spill`, задача 300);
- **происхождение переноса** — сообщение-перенос несёт идентификатор источника и «перенесено из …» по форме fork с `forked_from_id` (Codex `rollout/history`, задача 300); id сессии не перегенерируются и не получают алиасов (правило ZCode `docs/session-context-tool.md`);
- **разделение источник/видимость** — перенос не попадает в UI-проекции как обычное сообщение пользователя (образец: `subagent_message`, `visibility: model-only`, ZCode, задача 300);
- **граница обрезки по `keepID`** (opencode, 303 §6): граница «дословного хвоста» — идентификатор сообщения, а не число ходов; восстановление истории из записи точное;
- **два правила шаблона сводки** (opencode, 303 §6) — в наш `handoff_summary_prompt` (transfer.nv): выбрасывать пересылаемые заново инструкции (они впрыскиваются каждым агентом сам) и «новая история сильнее чекпоинта» при противоречии с прежней сводкой;
- **precompute сводки** (opencode, 303 §6): сводка переноса готовится заранее и держится неприменённой — смена агента не ждёт генерации.

**Результат:** спецификация формата + точка внедрения в этой папке.

**Приёмка:** владелец по спецификации и демо-переносу (после реализации отдельной задачей).

**Опора:** https://github.com/MoonshotAI/kimi-code, `packages/session-import` (MIT; чистая библиотека, код можно брать). Клон был в `%TEMP%\kimi-readonly`.
