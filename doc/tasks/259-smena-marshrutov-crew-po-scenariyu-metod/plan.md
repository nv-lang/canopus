## Предлагаемая вертикаль (не обещание готового локального фикса)

1. **Загрузка источника.** Прочитать таблицу раннера, реестр, журнал, библиотеки
   и вызываемые машины из явно настроенного checkout Методики @ `0e692ba…`.
   Проверить SHA и контрольные суммы; не менять product `dialog` и pin alula.
   Модуль загрузки — отдельный от `ProductMachines`: у методики есть собственные
   функции хозяина и вложенные машины. Не маскировать ошибки загрузки fallback-копией.
2. **Один нормативный runtime на задачу.** Сохраняемый движок раннера с состоянием `AlulaState`
   раннера, отдельно от chat/dialog. Именно раннер владеет маршрутом, эпохой,
   обязательствами, открытыми запросами и использованными ссылками. Данные панели —
   производная проекция, не вторая mutable-копия решения сценария.
   На pin `c040a9b` обычный `AlulaMachine.step` создаёт `ScriptedHost`
   (`alula.machine_run`, `machine.nv:47–52`), поэтому напрямую копировать runtime
   dialog недостаточно. Доступный API для настоящего хозяина — экспортированный
   `alula_step(machine, state, event, environment, host)` (`chain.nv:944`), принимающий
   протокол `PrimitiveHost.call_primitive(name, args)` (`alula.machine`, `eval.nv:68`).
   Требуется обёртка протокола `Machine` в Crew с делегированием только этому API,
   плюс сериализация/восстановление через `AlulaMachine.encode_state/decode_state`.
   Это host glue, не новый интерпретатор и не таблица переходов на Nova.
3. **Входы реальной работы.** Принятие новой задачи даёт `start` с папкой задачи и
   дерева. Выходной запрос `session_launch` связывается с реальным агентным ходом
   с сохранённым request id, а `loop_review` — с независимой проверкой и её id.
   Исходы передаются как типизированные ответы на исходные запросы; ни завершение
   произвольного хода, ни строка «зелёные тесты» не заменяют `SessionLaunchResult`
   или `ReviewResult`. Разбор артефактов обязан реализовать контракт источника.
   Нельзя сохранять собственный выбор следующей стадии в `route_next_step`
   для задач, которыми уже владеет машина.
4. **Смена во время работы.** UI передаёт ссылку на сохранённое решение;
   `change_route` подаётся существующему runtime задачи. Не вызывать `route_stop`.
   После подтверждённой записи шага публиковать проекцию нового маршрута.
   При активном запросе сохранить его id и дождаться настоящего исхода.
   При `SmenaZapisana` следующий отдельный сохраняемый вход — `continue_route`.
   Выбор следующей стадии остаётся строкам таблицы, не Nova-switch.
5. **Ворота и доверие.** Открытие из `record_route_gate` сохраняется идемпотентно
   по task+уникальному идентификатору открытия, а не task+имени состояния ворот.
   В источнике `task_runner.alula.md:493` идентификатор — `state + "-" + номер_ворот`;
   каждая запись содержит также epoch+subject+state. Повтор той же записи возвращает
   её, конфликт этих полей с прежним идентификатором — отказ, не перезапись.
   Разные открытия (в том числе тех же ворот/эпохи/предмета) сохраняются отдельно.
   UI показывает открытие только после подтверждения записи шага.
   Решение владельца хранится с task+gate+epoch+subject+reference и источником
   подтверждения; read-only verifier проверяет текущий subject, не погашая ссылку.
   Потребление ссылки — в сохраняемом состоянии машины. Прямой owner-ввод
   локального UI допустим лишь с честно описанной текущей моделью доверия;
   инструмент агента не должен создавать положительно проверенное owner-решение.
   Какой именно существующий owner-event использовать, ещё требуется подтвердить.
6. **Replay.** Сохранять сопоставление запросов машины и внешних операций до отправки;
   повторный запуск шага не должен создавать второй агентный ход/открытие ворот.
   После рестарта восстановить runtime, использованные ссылки и сопоставления,
   не «достраивать» разрешения по текущим воротам. Для acting-функций учитывать
   отступление источника: исполнение до сохранения; нужна идемпотентность хозяина.
7. **Старые задачи.** Сначала изоляция новых задач с явным opt-in в новый runtime,
   старые задачи продолжают работать прежним способом. Отдельная версия схемы и
   явный перенос из старого lifecycle:
   сохранить историю/счётчики, не выдавать старые approval за разрешения новых ворот.
   Пока нельзя достоверно сопоставить активную работу запросу — новый защищённый вход
   для этой задачи не включать. Самостоятельно останавливать существующую работу
   нельзя: при необходимости остановки переноса требуется отдельное решение владельца.

## Минимальный этап и оценка

Первый проверяемый этап — только новые opt-in задачи, реальный запрос агента с
сохранённым request id, смена во время него без cancel, фактический completion,
выбор следующего обязательства таблицей и восстановление той же цепочки после
рестарта; без git-публикации и без переноса старых задач. Этап не заменяет все
критерии приёмки 259. Красная проба обязана идти через текущий Hub, не статический
поиск имени `route_stop` и не mock таблицы переходов.

Предварительная инженерная оценка после выявления отсутствующих подсистем:
1–2 рабочих дня на минимальную вертикаль, 3–5 на полный объём с доказательствами,
replay и независимой приёмкой, при условии согласованного формата артефактов и
готового достижимого комплекта Методики. Это оценка, не обещание срока и не
самостоятельное разрешение расширить задачу. Ошибки meeting, формат артефактов,
owner-event и поставка остаются условиями до кода.
