# Короткий разбор и numbered brief

## Короткий разбор

Подтверждён дефект: `finishPrecheck` проверяет только непустоту `result`, а затем безусловно записывает `state: green`. Merge-путь доверяет этому состоянию. Структурная проверка текста результата не может подтвердить успех CI: минимально безопасная граница — строгий вердикт-протокол с точными SHA основы и кандидата, явными `pass`/`fail`/`unknown` и ссылкой/идентификатором запуска; плагин сверяет поля и Git-отношения, но не притворяется GitHub и не проверяет удалённый workflow. Ответственный приёмщик лично сверяет привязанный run к SHA и его итог до ввода `pass`; локальные тесты доказывают только обработку протокола. Любая иная форма fail-closed.

До выбора окончательной формы evidence и изменения общих продуктовых файлов жду точный seam от исполнителя и приёмщика 136: интегратор подтвердил разделение 140 (протокол/invalidate/merge guard) и 136 (cycle/lifecycle), сообщил, что 136 на доработке и попросил не предполагать порядок интеграции. Контакт с ними запрошен через интегратора.

Уточнение seam от интегратора (2026-10-21): 136 пока не принята, commit `e9347cd47da45bba27c6b4743f753e404ab75685`, dirty только `precheck.ts` и `crew-landing-precheck.test.mjs`; их исправление переносит cycle через finishPrecheck и проверяет mismatch cycle 2→1 в gateMerge. В 140 сохранять `rec.cycle` при GREEN, fail/invalidate/history; отказывать при несовпадении и гонках; старый GREEN/lock не переносить между циклами. Не брать и не копировать их незакоммиченный diff. Общие файлы разрешено менять по согласованному seam.

## Numbered brief

1. Сохранить текущую модель запуска precheck без merge-lock; начать запись с точного base SHA, зафиксированного от целевой ветки.
2. Заменить произвольный `result` явным вердиктом, содержащим версию протокола, `verdict` из `pass | fail | unknown`, exact `base` и exact `candidate` (полные SHA), и evidence CI: URL/идентификатор run и заявленный проверенный SHA/итог. Не принимать сокращённые хеши, веточные имена, пустые/неизвестные поля и несовпадения с записью `running`.
3. `pass` допускает переход в green только при корректной структуре и точном совпадении кандидата/основы. Это проверяет формат, привязку к записанным SHA, наличие Git-объектов, ancestry кандидата от base, неизменность задачи/круга и свежесть роли/записи. Машина не подтверждает удалённый статус CI или подлинность URL/run; это явно остаётся проверкой приёмщика. Без отдельного API/CI-orchestration нельзя заявлять автоматическое доказательство GitHub.
4. `fail` записывает отрицательный результат, сохраняющий base/candidate/evidence, время и автора; `unknown`, неуспешный CI, неполное evidence или протокольная ошибка не дают green. Ошибка запроса не стирает ранее сохранённые доказательства и не создаёт фиктивный отрицательный факт.
5. Добавить fail/stale/invalidate для назначенного приёмщика (или integrator) по своей задаче без lock и без смены task lifecycle. Нужны непустая причина, автор и время; сохранить прежнюю запись целиком в истории. Повтор для уже инвалидированной записи идемпотентен; поддельная роль, другая задача и конкурентное изменение/позднее завершение отвергаются.
6. Старые записи `green` без новой структуры verifiable evidence не являются свежими для merge после обновления. Отсутствие/невалидность протокола закрывает gate, без автоматической миграции существующих карточек.
7. Invalidate, finish и merge должны перечитывать одну актуальную запись; синхронная финальная проверка предотвращает гонку. Отрицательное или invalidated состояние не может захватить lock. Сохранять `rec.cycle` во всех переходах; отказывать при cycle mismatch/гонке и не переносить старый GREEN/lock между циклами. Переходы lifecycle из 136 не дублировать и не менять.
8. Минимальные различающие regressions: (a) синтетический RED carrier 092 не становится green; (b) unknown/empty/unsupported или несовпадающие base/candidate отклоняются без порчи evidence; (c) корректный положительный контракт даёт green только после нужной проверки, а fail/invalidate запрещает merge; дополнительно повтор invalidation, чужая роль/задача, устаревший ответ и гонка invalidate–finish/merge.
9. Документация README, crew_help, tool schema и тестовые снимки должны описывать один протокол, границу машинной проверки/приёмки и восстановление 092 штатной инвалидизацией с сохранением отрицательной истории; без ручной правки JSON, сдвига main или lock ради unlock.
10. Не читать/менять реальные данные Nova для тестов, не менять production 133/live/main, не мигрировать реальные карточки, не включать механизм и не пушить. Проверки: targeted regressions, guards; полный `npm test` только через очередь машины; независимая exact-SHA приёмка и свежие CI/precheck — не выдавать локальные пробы за GitHub.
