## Существенные замечания

### S1 — гонка между внешним spawn и закрытием не определена

- **Доказательство:** `spec.md:30–32` (REQ-03) требует атомарной сверки перед irreversible spawn, одновременно допускает, что close ждёт/видит точную running identity. В текущем `opencode-plugin/watch.ts:178–186` request переименовывается в claim, claim удаляется, затем `start()` отдельно создаёт detached child (`:103–116`), результат отдельно записывается. Файловая транзакция не охватывает OS spawn.
- **Критичность:** блокирует проверяемую реализацию: не определён арбитр, кто выигрывает между durable close и внешним запуском, что именно значит «close ждёт» и что происходит при падении после spawn до записи PID.
- **Почему:** обычный lock/rename сам по себе не может атомарно включить создание процесса; после crash нельзя узнать identity из ещё не записанного результата.
- **Исправление / уровень:** в следующей С1 уточнить допустимую гарантию и протокол: durable tombstone + сериализованный admission/start record, recoverable intent/identity и crash-point поведение; отдельно определить ограничения внешнего spawn и что считается STOP. Не обещать атомарность OS side effect.

### S2 — запрет «любого нового хода» сформулирован шире доступных потребителей

- **Доказательство:** `spec.md:38–40` (REQ-05) требует, чтобы система не создавала старой сессии prompt/command/retry/resume и не dispatch-ила сообщения; `:83–85` оставляет конкретные API неизвестными. В `opencode-plugin/index.ts:580–618` `resumeInterrupted()` и в `:624–641` `retryFailed()` создают письма по карточкам/обязательствам, не показывая проверку `spawned.status`; вызов `postLetter` отделён от внешнего OpenCode исполнения. `core.ts:3325–3333` закрывает карточку и obligation, но не устанавливает глобальный запрет новых ходов.
- **Критичность:** критический scope/AC разрыв: не перечислены все writers и фактический consumer, а критерий «никакого нового рабочего исполнения» не различает письмо в локальный inbox, API prompt и уже принятый ход.
- **Почему:** запрет на стороне CrewHarness не отменяет независимые действия клиента/сервера OpenCode; текущий API-инвентарь описывает операции, но не доказывает их гарантий.
- **Исправление / уровень:** С1 должна построить полную матрицу writer→queue→consumer для dispatch/retry/resume/commands и разделить гарантии на подконтрольные проекту и внешние; AC должен проверять каждый контролируемый путь и честно назвать остаточную внешнюю границу.

### S3 — REQ-04/06/08 требуют недостижимого общего доказательства остановки/изоляции

- **Доказательство:** `spec.md:34–36,42–44,50–52` требует точной process identity, остановки принадлежащих процессов и запрета старому процессу писать в scratch нового worker. Текущий `watch.ts:108–111` записывает только PID, запускает detached процесс, а `:220–228` вызывает `taskkill /T /F`, подавляет ошибку и всё равно пишет `done`/`code:null`. PID не задаёт неизменяемую identity и не доказывает отсутствие переподчинённых потомков или уже открытого файлового дескриптора.
- **Критичность:** блокирует приемлемость обязательного «выход доказан» и обещания изоляции; external process kill не даёт абсолютной гарантии без подходящей платформенной primitive/контейнера.
- **Почему:** exact ID в записи не равен OS handle; отсутствие процесса в одном snapshot не предотвращает будущий запуск и не закрывает уже выданные права записи.
- **Исправление / уровень:** план должен выбрать платформенные primitives и threat boundary, доказуемо ограничить права записи old process либо ослабить требование до «запретить контролируемые новые запуски; неизвестные потомки — STOP». AC покрывает PID reuse, reparenting и crash; не заявляет невозможное.
