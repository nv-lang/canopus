# Квалификация С5-1: результат не принят как доказательство достаточности/усложнения

Интегратор прочитал отчёт, manifest и все три скрипта. Исходные версии и семь raw
выводов наблюдений сохранены точными копиями во внешнем freeze; два заявленных
SHA stdout совпадают с первичными файлами. Ошибки первых запусков сохранены.
Spec не изменилась, production diff отсутствует, task idle/card busy=false,
своих незавершённых watches у автора нет. Это не global OS exit/fence proof.

## Существенные ограничения выводов

1. **Закрытие A в baseline-пробе не установлено.**
   `red-close-watch.mjs` создаёт request с произвольным session string, но не
   создаёт карточку/назначение A. Вызов `releaseExecutor` читает card и только при
   её существовании и spawned обновляет status. Поэтому возвращение функции здесь
   не доказывает даже fixture CLOSED, тем более C или successful close.
   Исправленная проба обязана показать начальное реальное состояние A и изменение
   её состояния по actual lifecycle пути. B также должна иметь явную identity.
2. **Проверено не заявленное queued-before-close расписание.**
   `pollWatches` вызывается до `releaseExecutor`: user process уже запущен.
   Это отдельный running-before-close случай, а не C до позднего admission/spawn.
   Нужны разные детерминированные сценарии: persisted/requested → close → poll;
   claimed → close → admission; admitted/running → C → terminal revoke. Не смешивать
   C и успешный close: spec разрешает ранее допущенный effect до отзыва его scope,
   но не разрешает success без terminal proof.
3. **Нет неизменного contract oracle RED→GREEN.**
   Baseline script утверждает `effectObserved === true` и завершается0: это
   диагностическое подтверждение наблюдения, не регрессионный тест запрета эффекта.
   Для предметной RED→GREEN нужен отдельный неизменный safety oracle, который на
   базе нарушается по целевому side effect, а на исправлении проходит; положительная
   B обязательна. Диагностический driver и его raw при этом не переписывать.
4. **Необходимость SQLite/native broker не доказана.**
   Tombstone проверен без межпроцессной сериализации; закрытие инжектируется после
   последней проверки. Это ограничение выбранного `check/use`, а не контрпример
   всем простым filesystem gate. Новый экземпляр класса не равен restart отдельного
   процесса. Отдельные D/C/terminal состояния в прототипе не реализованы, потому
   наблюдение side effect после записи C нельзя само по себе выдавать за нарушение
   всей таблицы spec. Нужна минимум проверка простого общего gate двумя реальными
   consumers и честное описание, что остаётся недоказанным в crash/OS/L.

## Итог и полномочия

Приняты только ограниченные наблюдения: baseline watch способен писать без
проверки owner lifecycle; persisted marker читается другим экземпляром класса;
проверка без общего gate оставляет окно между check и use. Полный L/T, безопасный
close, независимая B как security boundary и тяжёлая архитектура не доказаны.

С5-1 остаётся завершённой авторской попыткой5/5 с этим отрицательным выводом
квалификации; отчёт и история не переписаны. Не новая С2/С4, не независимая
приёмка продукта. Рекомендация владельцу: одна ограниченная доработка тех же P0–P2
обычным профилем, корректные lifecycle/расписания/oracle и простой общий gate;
никаких SQLite/native broker, broad integration, admin/live и снятия HOLD.
