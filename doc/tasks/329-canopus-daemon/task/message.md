## Суть

Хаб больше не спавнит агентов сам — ни локально, ни удалённо. Процесс агента (ACP по stdio) живёт внутри `canopus-daemon` на той машине, где идёт работа; хаб говорит с daemon'ом одним протоколом (ACP-кадры + монотонный seq + resume «отдай с последнего принятого»). Локальная машина — частный случай (loopback), удалённая — тот же daemon через WireGuard.

Что это даёт: один код-путь вместо двух; рестарт хаба и обрыв сети перестают убивать ходы (класс «тихих зависаний» 317/320 закрывается структурно); durable-очередь отправок (кандидат C самопроверки) поглощается буфером daemon'а.

## Этапы

1. **Локальный daemon.** Процесс-надзиратель на машине хаба: spawn/остановка агента, буфер кадров с seq, resume; хаб-адаптер транспорта (замена прямого spawn в `src/acp/`); красный тест: рестарт хаба посреди хода — ход доживает и догоняется.
2. **Удалённый daemon.** Тот же бинарь на Selectel: TCP только на адресе WireGuard, статический ключ в конфиге обеих сторон; проба спайка (разрыв 30 с → догон) как приёмочный тест; установка и починка — по документу `.selectel/BB/README.md` (образец).
3. **Enrollment и несколько машин.** Одноразовый ключ → постоянный, выбор машины при создании сессии — отдельным решением после этапа 2 (образец — enrollment bb).

## Границы

Не федерация хабов. Не изменение протокола хаб↔агент (ACP байт-в-байт тот же). Не перенос кода bb/спайка (Python-проба — только материал). Каждый этап — своя приёмка; этап 1 самодостаточен и приносит пользу без удалённых машин.

## Связи

Поглощает: кандидат C «durable-очередь отправок» (частично — письма `canopus_send` остаются на журнале хаба). Опирается на: 322 (waitingOn), 326 (коды ошибок), спайк 325. Конфликтует по коду с: `src/acp/` (клиент), `src/server/hub.nv` (spawn) — исполнителям текущих задач в этих файлах согласовывать очередь.
