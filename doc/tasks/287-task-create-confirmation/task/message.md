# Задание: Подтверждение создания задач и закрытие вопросов при отмене

Заказчик: владелец проекта. Дата задания: 2026-11-06.
Источник: чат владельца, подтверждение создания получено до резервирования номера.

## Чего хочет владелец

Владелец, 2026-11-06: «создаются задачи без подтверждения, поэтому много задач создаются дублей и не нужных, давай через подтверждение (через вопрос) делать».
Владелец, 2026-11-06: «в отмененной задаче висит вопрос, его надо отменять перед отменой задачи».
На вопрос о создании одной задачи после 285 владелец ответил: «Да, создать одну задачу после 285».

## Что нужно

1. Перед созданием задачи показать владельцу вопрос с названием, целью и результатом поиска возможных дублей. До подтверждения не создавать запись задачи, папку, рабочее дерево и исполнителя.
2. Одинаково защищать canopus_spawn, CLI и другие поддерживаемые точки создания. Слова агента не считать подтверждением владельца; решение связывать с конкретным предложением. Повторная доставка подтверждения не создаёт дубль.
3. Отказ или закрытие вопроса без ответа не создаёт задачу. После подтверждения задачу создавать ровно один раз.
4. Перед отменой задачи завершать её открытые native-вопросы и связанные ожидания; лишь после подтверждённого закрытия переводить задачу в отменённые. Ошибка закрытия должна оставлять видимую причину и возможность безопасного повтора.
5. Предусмотреть диагностику и исправление уже отменённых задач с зависшими вопросами без уничтожения истории.

## Критерии приёмки

- Без подтверждения владельца ни один поддерживаемый путь не создаёт задачу.
- Возможный дубль показан до подтверждения; повтор одного подтверждения не создаёт вторую задачу.
- Отказ и закрытие формы ничего не создают.
- После отмены задачи в её вкладке не остаётся открытого вопроса; отказ native-транспорта не выдаётся за успешное закрытие.
- Проверки охватывают создание, отказ, повтор подтверждения, отмену и сбой закрытия вопроса.

## Результат и куда он попадает

Механизм в плагине, MCP и CLI Canopus, адресные тесты и обновлённое правило Канона. Сначала согласовать план реализации; эта постановка не запускает реализацию.
