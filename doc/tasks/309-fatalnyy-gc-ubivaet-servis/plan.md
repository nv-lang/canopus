# 309. Фатальный GC «Too many heap sections» убивает живой сервис

**Инициатор и разрешение:** владелец, 2026-11-15, чат интегратора («да» — в ответ на рекомендацию завести задачу после второго случая).

**Факты:**
- 2026-11-14: посторонний процесс nova.exe (старый тулчейн 0.1.0) показал диалог «Fatal error in GC: Too many heap sections».
- 2026-11-15: живой сервис (папка установки, PID 78372, релиз-кит эпохи dbe7d0e8) найден мёртвым — порт 8099 не слушался; в `gc-лог рядом с программой сервиса (папка установки)` — то же сообщение: «Too many heap sections» (+ предупреждение о повторных больших аллокациях ~4100 KiB). Сервис перезапущен (PID 12756).

## Суть

Сервис периодически умирает фатальным сбоем сборщика мусора («Too many heap sections») без журнала, кроме gc-лога. Похоже на дефект памяти: либо разрастание секций кучи в нашем коде (утечка/неограниченный рост структур — например, журнал задач, кэш сессий), либо ограничение рантайма Нова (сборка GC / параметры кучи). Сервис должен деградировать или падать с диагностируемой ошибкой, а не исчезать молча.

## Что нужно

1. Собрать свидетельства: условия перед смертью (аптайм, нагрузка, объём журналов и state-файлов сервиса), полные gc-логи, дамп/метрики памяти.
2. Локализовать рост памяти: предположения — неограниченный кэш в хабе/роутах, копии больших строк (usage-логи, потоковые ответы), утечка соединений ACP.
3. Исправить: устранить рост в нашем коде; если предел в рантайме Нова — документировать лимит и (отдельно, через её интегратора) передать отчёт в Нова; по возможности настроить параметры GC/кучи при запуске.
4. Добавить наблюдаемость: сервис пишет причину падения (перехват fatal) или watch-скрипт фиксирует смерть и gc-лог.

## Критерии приёмки

- Воспроизводимый сценарий долгой работы сервиса без «Too many heap sections» (как минимум: контрольный прогон с мониторингом памяти).
- Причина локализована и записана в задаче; известен механизм падения.
