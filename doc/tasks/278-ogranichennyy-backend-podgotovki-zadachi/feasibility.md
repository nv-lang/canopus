# Реализуемость ограниченного backend

## Результат первичной проверки

Реальная граница для существующего произвольного ACP-драйвера не доказана.
Добавление серверного MCP allowlist само по себе её не создаёт. Рабочий
ограниченный backend пока не реализован; отрицательные проверки не пройдены.

### Проверенные точки

- `src/server/settings.nv`: `AgentSpec` содержит произвольные `program`, `args`,
  `ask`; нет проверяемого контракта отсутствия native tools.
- `src/acp/link.nv`, `keep_link`: процесс запускается через `Command.start`,
  с обычными правами процесса сервера. `cwd` не ограничивает доступ к файлам.
- `src/acp/client.nv`: callbacks `fs/*` и `terminal/*` не объявлены и
  отклоняются. Это не мешает инструментам, исполняемым внутри внешнего агента.
- `src/server/agent_config.nv`: существующая копия конфигурации сохраняет
  providers и другие plugins; при ошибке подготовки возможен запуск с исходной
  конфигурацией. Для защищённой Подготовки такой fallback недопустим.
- Прочитана постановка 271 из коммита
  `466d37fd95cd12b1b0b03acd35301b00df344883`: требуется защита даже при более
  широком родном режиме разрешений.

## Исключённый кандидат Claude CLI

Локальный `claude --help` сообщает следующие возможности:

- `--tools ""`: отключение всех встроенных инструментов;
- `--strict-mcp-config`: только явно переданные MCP-серверы;
- `--setting-sources`: выбор источников настроек;
- `--restricted`: исключение code-running tools и пользовательских/проектных
  настроек, но managed settings и `--settings` остаются применимыми.

Это кандидат для фиксированного специализированного launcher, а не разрешение
для произвольного ACP. Совместимость версии, отсутствие других каналов запуска
инструментов и реальный отрицательный тест ещё не проверены. Запуск модели
не выполнялся. Владелец, 2026-11-01, ответ на question этой вкладки:
«клод не оплачен». Кандидат исключён; проверять оплату платным запросом нельзя.

## Контрольная точка OpenCode

`opencode --version` вернул `opencode v2.0.26`. Production не менялся,
модель и новый сервис не запускались.

Текущая документация
<https://opencode.ai/v2/docs/build/plugins/server#generate-experimental>
описывает `ctx.experimental.generate.text` как генерацию без сессии и вызова
tools. Это кандидат для серверного цикла структурированных действий, а не
готовая замена ACP. Сверены опубликованные типы установленной версии:

- <https://unpkg.com/@opencode/plugin@2.0.26/dist/promise/plugin.d.ts>:
  `Context.generate: GenerateApi`; `experimental` содержит только `terminal`.
- <https://unpkg.com/@opencode/client@2.0.26/dist/promise/api.d.ts>:
  `GenerateApi = Client["generate"]`.
- <https://opencode.ai/v2/docs/providers>: runtime определяется `package`,
  настройки зависят от пакета; имя provider не подтверждает режим безопасности.

Таким образом, перенос примера из актуальной документации без сверки версии
неприемлем. Типы API не доказывают отсутствие provider-native tools, загрузки
проектных plugins и иных каналов выполнения. Нужны проверенный transport,
фиксированный provider/runtime, исключение переключения агента/provider и
воспроизводимая проверка фактической границы. Платный вызов не разрешён.

**Блокер текущего инкремента:** поддерживаемый backend с доказанным отключением
native tools в доступном запуске OpenCode не установлен. Это не доказательство
невозможности такого backend вообще. Добавление MCP поверх текущего ACP
не решает задачу и не выполняется вместо неё.

## Предлагаемый контракт с 271

1. Сервер проверяет backend перед spawn и перед каждым turn. Неизвестный или
   неподдерживаемый backend получает отказ, без fallback на обычный ACP.
2. Выбор режима native permissions не расширяет набор инструментов Подготовки.
   При переходе нельзя переиспользовать ACP-сессию с обычными инструментами.
3. Модель получает только `read_context` и `write_task_message`. Никаких общих
   инструментов маршрутов, исполнения задач, shell, execute, git или worktree.
4. `read_context` работает только с назначенными сервером файлами контекста.
   Проверки нужны для traversal, абсолютных путей, symlink/junction и выхода
   за список разрешённых файлов; доступ ко всему диску не подразумевается.
5. `write_task_message` принимает текст, но не путь. Цель назначает сервер;
   запись исходников и произвольных документов через этот инструмент невозможна.
   Начальный безопасный вариант — черновик в данных сессии. Назначение проектной
   постановки согласуется с 271 отдельно; никаких веток при записи не создаётся.
6. Backend считается доверенным исполнителем протокола, ОС-процесс сервера и
   администратор машины — вне модели угроз. Общая sandbox для произвольного
   исполняемого файла не создаётся.

Согласование с 271, 2026-11-01, переписка исполнителей: 271 самостоятельно
вносит fail-closed обычного ACP до spawn и защиту смены режима существующего
клиента. 278 `hub.nv` не меняет. 271 назначает session-owned цель
`<data_dir>/<session>/tasks/draft/task/drafts/<task_slug(title)>/task/message.md`.
Эта цель — контракт для будущего backend, а не разрешение произвольной записи.
Fail-closed 271 не объявляется готовой безопасной беседой.

## Доказательства, необходимые до сдачи реализации

- Успешные чтение разрешённого контекста и запись назначенной постановки.
- Отказ записи исходников, shell/execute, git/worktree, неизвестных tools,
  обходов путей и вызова общих серверных tools напрямую.
- Те же отказы при широких native permissions и после восстановления сессии.
- Неподдерживаемый backend отклонён до запуска; проверяется отсутствие spawn.
- Реальный поддерживаемый backend не получает builtin tools; тест с моделью
  дополняет, но не заменяет проверку фактического списка инструментов и dispatcher.

Ни один из этих пунктов сейчас не объявлен GREEN.
