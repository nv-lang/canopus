## Находки

1. **Контракт `fieldSchema` не определяет полностью закрытые вложенные схемы и их домены.**

   критичность: существенная — меняет допустимые payload, проверку совместимости bindings и возможность представить ограниченные числовые источники.

   уровень: требования

   **Цитата исходного требования:** `task/message.md:22`: «страж проверяет, что регламент соответствует закреплённой версии `task-runner.md`». По `task-algorithm.md`, шаг 3, constraints включают «ограничения API»; UNKNOWN нельзя превращать в FACT.

   **Место:** `spec.md:60–61,78,80,82`; REQ-23, REQ-27–28; AC-33, AC-37.

   **Цитаты спецификации:**

   - `fieldSchema`: «type-specific `enum`, `items`, `properties` only when applicable»; «array items required and maxItems bounded 1..10000; object properties/required required and closed».
   - «context registry — имена outputs, fieldSchema результата».
   - «тип/domain/nullable источника должны быть подмножеством типа получателя».
   - «set требует ненулевой valueBinding совместимого типа».

   **Доказательство:**

   - Для `maxItems` не определены точный тип и обязательность. Форма array с `items`, но без `maxItems`, не получает однозначного результата: `items` прямо required, `maxItems` только bounded.
   - Для вложенного object упомянут `required`, но не определены его тип, уникальность и отношение к `properties`. Не установлено, используется ли там `additionalProperties:false`, как у `payloadSchema`, или запрет дополнительных свойств неявный. Разрешённые ключи конкретных ветвей union не перечислены полностью.
   - `fieldSchema` для integer не имеет объявленного числового домена. Поэтому context output, ограниченный, например, положительными целыми, нельзя отличить по объявленной форме от произвольного integer. Это существенно для `set/recompute` в counter с `bounds.min=1`: требование о совместимости доменов есть, а место декларации такого домена отсутствует.
   - Внешний registry не устраняет пробел автоматически: его context output прямо описывается той же `fieldSchema`. Если ограничения предполагается хранить отдельно в signature, их структуру и связь здесь необходимо назвать.

   Проба П3 осмотрела обе составные ветви и соответствующие правила bindings. Это не прогон валидатора и не утверждение, будто любой nested object безусловно запрещён: проблема — неоднозначность полного закрытого контракта.

   **Исправление:** задать точные ветви `fieldSchema`, required/optional поля, их типы и ограничения; определить, где декларативно представлены домены, используемые при совместимости bindings. Выражения и пользовательский код для этого не нужны.

2. **`progressFormat.nSourceRules` остаётся массивом без формы элементов и разрешения ссылок.**

   критичность: существенная — не позволяет однозначно проверить обязательное поле и источник знаменателя прогресса.

   уровень: требования

   **Место:** `spec.md:50,74,78,342–344`; REQ-08, REQ-19; AC-15.

   **Цитата спецификации:** «`nSourceRules:array`»; рядом для `linePattern` задана точная запись `{id,grammar,hasDate:boolean,unitRule:string}`. В примере: `"nSourceRules":["unit.spec"]`.

   **Доказательство:** во всех 44 строках таблиц и последующих инвариантах нет формы элемента `nSourceRules`: строка, ID правила или объект. Не установлены каталог адресации, уникальность и связь с `linePatterns[].unitRule`. Непустота массива не отличает `["unit.spec"]` от `[1]` или `[{}]`.

   UNKNOWN-07 допускает отсутствие конкретного unit registry, но не заменяет определение формы поля самого регламента.

   **Исправление:** определить тип элементов, namespace/binding и отношения с line patterns; добавить положительную и отрицательную пары.

3. **Общее правило `N имени равен summary.N` не применимо к `facts-N.md`.**

   критичность: существенная — меняет допустимость обязательного машинного семейства документов совещания.

   уровень: требования

   **Цитата источника:** закреплённый `task-runner.md:74`: строки `facts-N.md` начинаются с «`наблюдалось:`», «`не наблюдалось:`», «`не измерено:`» или «`вывод:`»; «последняя строка `не читал: <перечень>`». Строка 331 связывает `facts-n.md` с заходом `n`.

   **Место:** `spec.md:46,88,204`; REQ-15; AC-14, AC-28.

   **Цитата спецификации:** «Повтор токена запрещён; N имени равен summary.N, round — feedback round».

   **Доказательство:** для законного `facts-2.md` источник не предусматривает summary. Добавить первую строку `Заход 2: …` нельзя без нарушения собственной формы файла фактов. Но действующая общая норма требует равенство с отсутствующим `summary.N`.

   `{N}` нужен этому семейству, поскольку это номер захода, а не feedback round или номер линзы. Правило должно различать документы со summary и без неё. Предоставление grammar registry само по себе не отменяет общего инварианта строки 88.

   **Исправление:** ограничить равенство со summary соответствующими семействами; отдельно определить binding номера захода для `facts-{N}.md`.
