# Спайк: удалённый исполнитель — резидентный ACP-прокси на Selectel через WireGuard

## Чего хочет владелец

Владелец, 2026-11-27, чат интегратора: исполнение задач на удалённой машине в контуре Канопуса (наши машины-состояния, журнал, приёмка). Голый SSH как транспорт живого ACP-канала отвергнут (обрыв = смерть stdio = смерть хода). Владелец, 2026-11-27: «по рекомендации» — завести спайк после задач 322/323.

## Что нужно

Спайк (исследование с пробой, не продукция): на Selectel (Ubuntu 24.04, доступ по ssh, WireGuard на ноутбуке есть) поднять минимальный резидентный прокси:

- демон `canopus-acp-proxy` (systemd): держит процесс агента у себя (агент живёт независимо от связи с хабом), слушает TCP только на адресе WireGuard, буферизует события с seq и умеет resume («отдай с последнего принятого»);
- хаб подключается к прокси вместо локального spawn: протокол ACP байт-в-байт тот же, меняется только транспорт одной связки; обрыв WG = переподключение с курсором, ход не умирает;
- статический ключ в конфиге обеих сторон (enroll-инфраструктура bb не нужна — машина одна).

Проверка на тестовой сессии Kimi: запуск задачи → обрыв WG на 30 с → догон событий → завершение хода. Отдельно снять поведение агентов при переподключении клиента посреди хода (по образцу проб steer-спайка).

Результат: документ в doc/research/ с вердиктом «реализуем / цена / пределы» и формулировкой продуктовой задачи. Общий seq/resume-механизм в перспективе разделяется с live-каналом страницы и CLI (см. разбор в doc/research/2026-11-26-bb-protocols.md, «Что перенести»).

## Границы

Не федерация хабов, не мультимашинность общего вида (несколько машин — следующий шаг после вердикта). Образец семантики — bb (демон, seq/ack-resume, исходящее соединение), код не переносится.
