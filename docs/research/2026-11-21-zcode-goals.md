# Как ZCode работает с целями: постановка, шаги, критерий приёмки, автозапуск (исследование 2026-11-21)

Раздел «что перенести» отобран по критериям [doc/research/README.md](README.md).

Повод: владелец спросил, как устроены «цели» в ZCode (z.ai code) и что из этого стоит перенести в Канопус.
Источник — открытый репозиторий `zai-org/ZCode` (Apache-2.0), **shallow-клон только для чтения**, ревизия
**`fec975905a2abd4c07e35c40d51fa097a2258ec9`** (глубина 1). Основной код — TypeScript:
`apps/zcode-cli/packages/{contracts,core,adapters,bootstrap}`, документация — `docs/chat/goal-*.md`,
`docs/conversation-protocol-declaration.md`, матрицы покрытия. Ниже — чтение исходников, без запуска.

Обозначения: **[V]** — проверено по коду/документу (путь:строка); **[I]** — вывод.

## Главное

- Цель в ZCode — это **`session_target`**: одна долгоживущая цель на сессию, постановка **только пользовательской
  командой** `/goal`/`/target`; у модели есть лишь чтение (`GoalRead`). **[V]**
- После каждого хода рантайм сам запускает **проверку завершения** отдельным модельным запросом («verifier»), и,
  если цель не принята, — **следующую итерацию** (model-only вход) с подсказкой из вердикта. **[V]**
- Приёмка — структурированный JSON `{passed, reason, nextAction}` с жёсткими правилами «доказательств по каждому
  требованию»; ошибка самого verifier’а — **fail-open** (проходит), чтобы невиновный не застрял в вечном цикле. **[V]**
- Статусы: `active`, `paused`, `budget_limited`, `complete`. Бюджет — только токены, необязательный; время — учёт,
  а не лимит. **[V]**

## 1. Когда ставится цель

- Команды: `/goal <objective>`, `/target <objective>`, `/goal replace`, `/goal resume`; `pause`/`resume`/`clear` —
  управление состоянием, а не обычный prompt (`docs/chat/goal-query-readonly.md`, `goal-command-running-guard.md`). **[V]**
- В running или compacting цель **не вклинивается**: `/goal` уходит в очередь сессии как элемент `kind=goal`
  (FIFO), применяется при освобождении; очередь с «paused» требует явного подтверждения пользователя
  (`docs/conversation-protocol-declaration.md:212,229`). **[V]**
- В plan-режиме `/goal` из composer’а только показывает toast и не создаёт цель
  (`docs/testing/conversation-session-goal-specific-coverage-matrix.md`, G0-11). **[V]**
- Пока цель не `complete`, обычная очередь **не дренируется**: `active/paused/budget_limited` блокируют text, goal и
  compact (`conversation-protocol-declaration.md:222`). **[V]**
- Модели доступен только `GoalRead` («Read the current session goal and status», read-only)
  (`core/src/tool/handlers/target.ts:31-49`). Создание/замена — прерогатива пользователя; самовольная постановка
  модели невозможна. **[V]**
- Схема цели (SQLite `session_target`): `target_id, objective (≤4000 симв.), summary_title, status, token_budget?,
  tokens_used, time_used_seconds, active_input_id?, active_run_started_at_ms?, active_run_last_seen_at_ms?` —
  `contracts/src/tools/target.ts:44-87`, `adapters/src/storage/session-target.ts:13-30`. **[V]**

## 2. Как строятся шаги и «план»

- Рантайм-плана у цели нет. Шаги — это (а) `TodoWrite`-список сессии и (б) подсказки автопродолжения; панель
  резюме показывает актуальный `plan`, если он есть, иначе последнюю группу `todoGroups` — не сумму всех групп
  (`docs/chat/goal-todo-summary-restore.md`). **[V]**
- Итерации цели нумеруются **по lifecycle проверки**: новая итерация начинается только со старта
  `target_completion_verification`; обычные ходы, ручное «продолжить» и TodoWrite итерацию не двигают
  (`docs/chat/goal-verification-divider.md`). **[V]**
- В plan-режиме автопродолжение цели вообще выключено: кандидат продолжения возвращает `null`, если включён plan
  (`core/src/runtime/methods/target.ts:190-200`). **[V]**
- Промпт продолжения (`contracts/src/tools/target.ts:139-211`) содержит: статус/токены/остаток, objective как
  **недоверенные данные**, «не повторяй сделанное, выбери следующее конкретное действие» и чек-лист аудита
  завершения (разложить objective на требования, сопоставить каждому доказательство, «прокси-сигналы не считаются»,
  «сомнение = не сделано») и прямое: **«не закрывай цель сам — рантайм запустит verifier»**. **[V]**

## 3. Критерии приёмки

- Отдельного поля «критерий» нет; приёмка — автоматический **verifier** (`target_completion_verification`):
  отдельный модельный запрос той же модели сессии, запрещено «делать работу, писать файлы, вызывать инструменты»,
  ответ строго `{"passed": boolean, "reason": string, "nextAction": string}`
  (`contracts/src/tools/target.ts:212-246`, `core/.../target-completion-verification.ts:17-100`). **[V]**
- Правила verifier’а: сначала классифицировать objective (разговорные нет-задачи — приветствие/спасибо — проходят
  без артефактов, чтобы не крутить бесконечные итерации); затем чек-лист «prompt→artifact» по каждому требованию,
  Named-file/command/test/gate/deliverable; «грин-тест или манифест — доказательство только если действительно
  покрывает требование»; TodoWrite с `pending/in_progress` → fail с `nextAction` на завершение незакрытого todo;
  «assistant говорит, что невозможно» — это свидетельство, но не доказательство: verifier обязан проверить сам
  (`target.ts:212-246`). **[V]**
- Вердикт: `passed=true` → цель переводится в `complete` (runtime, событие `status_updated`)
  (`target-completion-verification.ts:74-92`); `passed=false` с `nextAction` → следующая итерация с этим
  `nextAction` в заголовке; `passed=false` **без** `nextAction` — сбой самого verifier’а, продолжение **не**
  запускается (`core/.../target.ts:106-125`). **[V]**
- Сбой verifier’а (битый JSON/инфраструктура) — **fail-open**: считается `passed=true` с причиной в журнале/UI,
  чтобы уже сделанная работа не застряла из-за судейской поломки (`target.ts:279-330`, `goal-verification-divider.md`). **[V]**

## 4. Как обеспечивается автовыполнение

- После хода рантайм ставит команду `target-continuation` (`continueActiveTargetIfIdle`,
  `core/src/runtime/methods/target.ts:36-66`). Кандидат продолжения: нет активной/очередной работы, план-режим
  выключен, сессия сохранена, цель `active` (`target.ts:176-200`). **[V]**
- Перед продолжением — verifier (`verifyBeforeContinue`); если идут фоновые задачи — продолжение откладывается
  («deferred while background tasks are running», `target.ts:87-104,203+`). **[V]**
- После verifier’а цель **перечитывается**: если её успели остановить/сменить, продолжение не запускается
  (защита от гонки «Stop во время проверки», `target.ts:127-146`). **[V]**
- Сам ход продолжения — `model-only` вход (`inputVisibility: "model-only"`, `inputSource: "goal-continuation"`),
  с тем же `inputId`, что и исходный ход, чтобы UI не путал его с новым пользовательским сообщением
  (`target.ts:148-190`). **[V]**
- **Бюджет токенов**: переключение в `budget_limited` делается на уровне учёта в SQL —
  `when status='active' and token_budget is not null and tokens_used + delta >= token_budget then 'budget_limited'`
  (`session-target.ts:271,370`); `budget_limited` ведёт себя как пауза — автопродолжения нет, нужен явный `resume`
  (`projection-rows.ts:172`). **[V]**
- **Учёт времени**: `timeUsedSeconds` + открытый интервал `activeRunStartedAtMs`; `pauseGoal` сначала фиксирует
  интервал, затем пауза; `resumeGoal` открывает новый интервал без сброса накопленного; UI тикает отображение
  локально и не пишет в хранилище (`docs/chat/goal-elapsed-accounting.md`). **[V]**
- **Fork**: копируется `session_target` с тем же `target_id` и временем создания, и только verifier-записи до точки
  форка с переякорением `anchorAssistantMessageId`; очередь родителя не копируется, `active_run_*` в ребёнка не
  переносятся (`docs/chat/goal-session-fork-state.md`, `session-target.ts:64-100`). **[V]**
- Завершение цели при паузе/стопе: `pauseGoal` — отдельное продуктовое состояние (сначала фиксация времени,
  потом пауза), не то же, что stop («stop» только прерывает текущий прогон). **[V]**

## 5. Что стоит перенести в Канопус (идеи)

1. **Цель ставит только владелец, модель — только читает.** У нас цель может ставить модель; полезно развести
   «постановка» и «исполнение» так же, особенно для автономных ходов. **[I]**
2. **Автоматический «судья» с ограниченным запросом**: отдельный вызов «проверь завершение, работу не делай»,
   JSON `{passed, reason, nextAction}`; вердикт — данные, а не текст. **[I]**
3. **Политика «нет nextAction — не продолжать»**: сбой судьи не превращается в бесконечные итерации. **[I]**
4. **Fail-open у судьи** с явной пометкой в журнале/UI — прямолинейно спасает от «застрял из-за инфраструктуры». **[I]**
5. **Итерации нумеруются проверкой, а не ходами** — чистая метрика прогресса и стабильная привязка к ответу. **[I]**
6. **Продолжение как model-only вход с тем же `inputId`** — не плодит фальшивые пользовательские сообщения. **[I]**
7. **Plan-режим выключает автопродолжение**, фоновые задачи откладывают его, после судьи цель перечитывается
   (защита от Stop/подмены). **[I]**
8. **Классификация «разговорная нет-задача»** в судье — антидот от бесконечного продолжения на «привет/спасибо». **[I]**
9. **Бюджет как отдельный статус** `budget_limited` (пауза-как-лимит) и SQL-переход на учёте, а не догадка модели. **[I]**
10. **Fork-инварианты цели**: тот же target_id, verifier только до точки форка, без очереди и без active-run —
    хорошо ложится на нашу передачу контекста (298). **[I]**

## 6. Отличия от Kimi Code и Codex (см. соседние исследования)

- ZCode: цель ставит **только пользователь**; у Kimi и Codex цель может создавать модель по явной просьбе. **[V/I]**
- ZCode: приёмка — **автоматический судья** с JSON-вердиктом и fail-open; у Kimi — аудит моделью по тексту;
  у Codex — аудит моделью плюс рантайм-детекция тупиков. **[I]**
- ZCode: итерации/расход/время — продуктовые поля цели; Kimi — бюджеты turns/tokens/time; Codex — только токены. **[I]**
- Общее у всех трёх: автопродолжение отдельным системным входом, objective как недоверенные данные, «слабое
  доказательство ≠ сделано», пауза/резюм только пользователем. **[V]**

## Ограничения исследования

- Часть документов в репозитории на китайском; смысл передан, точные формулировки — по ссылкам. **[I]**
- Клон глубины 1 и ревизия `fec97590` — снимок; UI-часть (verifier divider, panels) просмотрена выборочно. **[V]**
- Матрица покрытия отмечает часть goal-сценариев как `undefined/missing` (429/503/SSE-обрывы, диск, вытеснение
  очереди) — поведения при этих сбоях у продукта ещё нет; в наши решения их не переносить как «готовое». **[V]**
