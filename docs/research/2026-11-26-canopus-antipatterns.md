# Самопроверка Канопуса по антипаттернам конкурентов (исследование 2026-11-26)

Самопроверка Канопуса по мотивам [2026-11-26-competitors.md](2026-11-26-competitors.md): четыре антипаттерна,
на которых хрупки/мертвы конкуренты (vibe-kanban, crystal), плюс эталоны bb
([2026-11-26-bb-architecture.md](2026-11-26-bb-architecture.md),
[2026-11-26-bb-messages-tasks.md](2026-11-26-bb-messages-tasks.md)). Ссылки на код Канопуса — от текущего main
(`2614bdae`), `путь:строка`.

Обозначения: **[V]** — проверено по коду; **[I]** — вывод.

## Главное

Из четырёх смертельных антипаттернов конкурентов у Канопуса **нет ни одного в чистом виде**; два пункта —
«частично» (текстовые классификаторы на границе ACP, очередь отправки в памяти), три недобора до эталона bb. **[I]**

## Чисто: антипаттерна нет

1. **Id минтим мы, не провайдер.** Сессию хаба создаёт хаб: id (`trace`) валидируется и становится
   `Dialog { id: trace, ... }` (`src/server/hub.nv:1707-1717,1741`); дочерние сессии минтит сам хаб
   (`cs_make_session`, `hub.nv:1686`). ACP-`sessionId` вылавливается из `session/new`, но используется только
   как фильтр протокола: апдейт чужой сессии отбрасывается с заметкой (`src/acp/client.nv:505-511,563-566`);
   наружу как идентичность не протекает. Номера запросов считает механика движка («Номер запроса —
   `<сторона>-<попытка>`», `machines/product/dialog.alula.md:9`). Это то, на чём погиб vibe-kanban (id из
   потока агента). **[V]**
2. **Занятая сессия — очередь, не отказ.** У клиента явная очередь `queue []AcpQueued`
   (`src/acp/client.nv:39,88`): `send` всегда ставит в очередь — «queues the request (one turn at a time, in
   the order of sending)» (`client.nv:1122-1134`); помпа берёт следующий, только когда ход свободен
   (`client.nv:955,961-962`). Плюс хаб держит сообщения, ожидающие готовности дерева, — `HeldMsg`
   (`hub.nv:294-295`). Steer «влить в текущий ход» нет, но есть протокольная отмена хода (`cancel_request`,
   `client.nv:1143-1145`) и возврат текста в редактор при недоставке (`src/web/delivery.js:6`). Это то, на чём
   хрупок crystal (исключение вместо очереди). **[V]**
3. **Единая точка dispatch — сильнее, чем у bb.** Все события идут через один движок-состояниемашину (таблица
   `machines/product/dialog.alula.json`, интерпретатор AlulaMachine): вход — `feed_in`/`accept_in` →
   `Engine.step` → приказы → `@drain` (пример `hub.nv:1692-1695`). Хаб не разбирает семантику ходов — только
   транспорт. Состояние ожидания экспонируется (`open_ids()`, `hub.nv:3422`; `@machine_line`, `hub.nv:914`;
   `list_status: "waiting"`, `hub.nv:841`; `mcp_waiting`, `hub.nv:2089`). **[V]**
4. **Провайдер-шов закрытой грамматикой.** `project_update` маппит ACP-апдейты в фиксированный набор проекций
   (`agent_chunk`, `agent_thought`, `tool_call`, `plan`, `usage_update`, …), неизвестное → `skipped`
   (`src/acp/project.nv:224-254`); `progress_event` заворачивает в типизированный `Incoming` движка, всё без
   запроса — сигнал `acp_note` в журнал (`project.nv:564-570`); хаб признаёт только белый список имён
   (`hub.nv:2602`). Таймлайном владеет движок/журнал, не клиент: «the journal alone tells the whole story
   after a restart» (`hub.nv:15`). **[V]**

## Частично: слабые места

1. **Матчинг текстов на границе ACP.** Ядро типизировано: закрытый `FailCode` (`MaxTokens`,
   `MaxTurnRequests`, `ModelRefused`, `StoppedByHuman`, `NoResult`, `Timeout`, `CeilingReached`), маппинг
   stopReason → код таблицей, неизвестное → `NoResult` (`src/acp/project.nv:578-587`); UI показывает причины по
   кодам (`src/web/delivery.js:19-22`). Но на границе, где ACP кодов не даёт: переполнение контекста —
   `contains("context_window_exceeded") || contains("context window") || contains("prompt is too long")`
   (`src/acp/client.nv:557-560`, вызов `:550`); «нужен логин» — `lower.contains("login") ||
   contains("unauthorized") || contains("401") || …` (`src/server/hub.nv:1189`); матчинг своих префиксов
   (`hub.nv:3497`); regex-санитайзер показа ошибок (`src/web/delivery.js:11,18-34`). Recovery-решения
   принимаются по типам; текст — только классификация того, что провайдер отдаёт текстом. Хрупко по природе. **[V]**
2. **Очередь отправки в памяти.** `AcpClient.queue` и `HeldMsg` при рестарте теряют недоставленные отправки:
   сообщение в журнале остаётся, но агенту автоматически повторно не уходит. При этом состояние ходов — не в
   памяти: истина — журнал; при старте каждая сессия восстанавливается из снапшота+журнала
   (`hub.nv:1394-1408,1494-1515`). Незавершённый ход после рестарта — не молчаливый resume и не мгновенный
   failed: тишина отсчитывается от последнего живого события (`hub.nv:1508-1515`), машина закрывает ход
   типизированным сроком `no_answer_in_time` (`machines/product/dialog.alula.md:91`), второй эшелон — watch с
   видимой ошибкой и записью в лог (`hub.nv:3417-3433`). Поздние MCP-ответы — честный stale-протокол:
   «stale, не разрешение действовать» (`hub.nv:174-178,2028-2033`). Доставка страница→хаб переживает рестарт:
   durable-outbox в localStorage + журнальные квитанции `message_delivery` с дедупом по `client_id`
   (`src/web/delivery.js:1-2,39-56`; `hub.nv:103-107`). Это уровень cline «interrupted — never silently
   resumed». **[V]**

## Недобор до эталона bb

1. **Нет человекочитаемого waitingOn** («чего именно ждём») для UI: состояние машины экспонируется, но
   дословной причины ожидания, как словарь `waitingOn` у bb, нет. **[I]**
2. **Нет durable-очереди недоставленных сообщений** (аналог `queued_thread_messages` с claim/CHECK) — прямой
   кандидат из «что перенести» ([2026-11-26-bb-messages-tasks.md](2026-11-26-bb-messages-tasks.md), п. 1-2);
   закрывает слабое место «частично-2». **[I]**
3. **Live-канал без ack в сторону страницы**: delta-resume по `{count, last-id}` есть (`hub.nv:893-916`), но
   подтверждений приёма, как `{seq, ack}`-кадры демона bb, нет. **[I]**

## Вывод

Архитектурные решения Канопуса (журнал как истина, машина-состояний как единый dispatch, id у хаба, закрытая
грамматика шва) совпадают с тем, что у выживших конкурентов (bb, opencode, cline), и избегают того, на чём
погибли vibe-kanban и crystal. Добить до эталона: durable-очередь отправки, waitingOn-тексты, типизация
текстовых классификаторов на границе ACP (или их изоляция за одним модулем с тестами-фикстурами). **[I]**

## Рекомендации к решению (2026-11-26)

Порядок — по отношению «польза/цена»; каждый пункт — кандидат в задачу обычным порядком (постановка — через
подтверждение владельца). Доноры указаны для чтения идей, код не переносится.

1. **Durable-очередь недоставленных отправок** (закрывает «частично-2»). Сейчас `AcpClient.queue` и `HeldMsg`
   в памяти: рестарт теряет отправки, журнал о них знает, но повторной доставки нет. Решение по образцу
   durable-инбокса opencode (`packages/schema/src/session-inbox.ts:11`) и очереди bb
   (`packages/db/src/schema.ts:1084`): недоставленная отправка — запись в журнале сессии (у нас журнал уже
   истина — новой БД не нужно), при восстановлении сессии (`hub.nv:1494-1515`) недоставленные записи
   переподаются в помпу. Инварианты взять у cline: «running rows are marked interrupted — never silently
   resumed» и идемпотентный admission opencode («first admission wins» — дедуп по `client_id` у нас уже есть в
   `message_delivery`, `hub.nv:103-107`, распространить на агентскую сторону). Красный тест: рестарт хаба с
   непустой очередью → отправки доезжают ровно один раз. **[I]**
2. **WaitingOn-тексты для UI.** Состояние ожидания уже экспонируется (`hub.nv:841,914,2089,3422`) — добавить
   закрытый словарь причин с дословными строками, как у bb
   ([2026-11-26-bb-messages-tasks.md](2026-11-26-bb-messages-tasks.md), раздел 1.3: «the thread is already
   running a turn» и т.п.). Цена — одна таблица «состояние машины → строка»; польза — конец классу «тихих
   зависаний» (320) на уровне UI. Красный тест: каждое ожидающее состояние машины имеет строку, пустых нет. **[I]**
3. **Изоляция текстовых классификаторов границы ACP.** `acp_context_overflow` (`src/acp/client.nv:557-560`) и
   детект логина (`hub.nv:1189`) — неизбежный текстовый разбор того, что провайдер отдаёт текстом. Не убрать,
   а обуздать: собрать все такие матчеры в один модуль (одна таблица «паттерн → типизированный код»), покрыть
   фикстурами реальных текстов ошибок провайдеров (по образцу record/replay opencode http-recorder — кассеты
   без живого провайдера), при неизвестном тексте — честный `NoResult`, а не догадка. Это же готовит почву для
   типизированных recovery-hints bb (`docs/provider-bridge-protocol.md:371-421`), когда ACP их даст. **[I]**
4. **Ack в сторону страницы** — самый дешёвый и самый необязательный пункт: delta-resume по
   `{count, last-id}` (`hub.nv:893-916`) уже не теряет данные; ack добавил бы только раннее обнаружение
   расхождения. Делать последним или не делать вовсе, пока не появится симптом. **[I]**

Общая граница: все четыре пункта — внутри существующих механизмов (журнал, машина, один модуль), новых
хранилищ и процессов не требуется; live-система затрагивается только пунктом 2 (строки UI). **[I]**
