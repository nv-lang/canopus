# Как Kimi Code работает с целями: постановка, план, критерии приёмки, автозапуск (исследование 2026-11-21)

Раздел «что перенести» отобран по критериям [doc/research/README.md](README.md).

Повод: владелец спросил, как Kimi Code устраивает «цели» и что из этого стоит перенести в Канопус.
Источник — **установленный пакет** `@moonshot-ai/kimi-code` версии **2.1.1** (дистрибутив от 2026-10-08): собранный
`dist/main.mjs`, в котором сохранены исходные описания инструментов и напоминаний с путями вида
`packages/agent-core-v2/src/features/goal/...`. Живых прогонов не делал: всё ниже прочитано в бандле.

Обозначения: **[V]** — проверено по коду/строкам бандла; **[I]** — вывод или недоподтверждённая деталь.

## Главное

- Отдельного «плана» у них нет. Цель — **контракт завершения**: `objective` + необязательный
  `completionCriterion` + бюджеты; маршрут по шагам каждый ход прокладывает модель, а рантайм гарантирует
  продолжение, учёт и остановку. **[V]**
- Исполнение держат три механизма: (1) напоминание о цели, впрыскиваемое в каждый ход; (2) автопродолжение
  хода системным триггером `goal_continuation`; (3) жёсткие бюджеты и гардовая проверка на старте хода. **[V]**
- Состояние цели **долговечно**: события `goal.create` / `goal.update` пишутся в журнал сессии с актором
  (`user/model/runtime/system`) и числами расхода; после перезапуска состояние восстанавливается нормализацией. **[V]**
- Objective всегда подаётся модели как **данные** (`<untrusted_objective>`), а не инструкции. **[V]**

## 1. Когда ставится цель

- Инструмент `CreateGoal` (только у главного агента: «Goal tools are only supported by the main agent»). **[V]**
- Схема: `objective: string (min 1, "must have a verifiable end state")`, `completionCriterion?: string`,
  `replace?: boolean` («replace an existing active, paused, or blocked goal instead of failing»). Файл
  `features/goal/tools/create-goal/create-goal.md`. **[V]**
- Политика вызова (текст инструмента): создавать только если пользователь явно просит цель/автономную работу или
  хост прислал goal-intake; **не** создавать для приветствий, обычных вопросов и расплывчатых просьб без проверяемого
  конечного состояния; при расплывчатости — спросить критерий, при настойчивости пользователя — создать. Длинные
  ТЗ — ссылкой на файл, не копипастой. **[V]**
- Встроенный скилл `write-goal` помогает сформулировать цель: что должно стать истинным, **чем это доказывается**,
  где граница работы, **когда остановиться и доложить**; формулировка согласуется с пользователем, `CreateGoal`
  вызывается после согласования, и перед запуском пользователь получает финальное подтверждение. **[V]**
- Очередь: `/goal next <objective>` ставит следующую цель, `/goal next manage` — менеджер очереди
  (правка/удаление/перестановка). Когда текущей цели нет и агент свободен, следующая из очереди поднимается
  автоматически (promotion с таймером и защитой от гонок). **[V]**
- Команды: `/goal` (поставить), `/goal resume`, `/goal next …`; отмена — `Goal cancelled`. **[V]**

## 2. Как строится «план» выполнения

- Плана-структуры нет; есть итеративный режим. На каждый ход при активной цели впрыскивается
  `features/goal/injection/goal-active-reminder.md` **[V]**:
  - objective и критерий — как **данные** (`<untrusted_objective>`), статус, прогресс, бюджеты и остатки;
  - «держи самоаудит кратким», «выбери один ограниченный полезный кусок работы», «не исследуй посторонние
    трактовки», перед работой проверить, нет ли в запросе явного лимита, и при наличии — сначала `SetGoalBudget`.
- Модели прямо предписано: завершил полезный кусок при оставшейся работе — **заверши ход нормально**, не закрывай
  цель; рантайм попросит продолжить. То есть пошаговое планирование — это «один слайс на ход», а не дерево задач. **[V]**
- Прежние ходы при этом сжимаются штатной компакцией контекста (skill/compaction в том же бандле) — отдельного
  «плана цели» не сохраняется. **[I]**

## 3. Критерии приёмки

- `completionCriterion` — необязательное поле, но главный носитель приёмки: «how to verify the goal is complete,
  include when the user provides one». **[V]**
- Правила `complete` (из `update-goal.md`): цель выполнена, **и заявленная проверка пройдена**; сверить состояние с
  objective и **каждым** явным требованием; «слабое или косвенное доказательство считать незавершённостью»; нельзя
  закрывать из-за исчерпания бюджета или желания остановиться. **[V]**
- `blocked` — только подлинный тупик (внешнее условие, нужен пользователь, нет прав/учёток, устойчивый сбой,
  невозможная/небезопасная/противоречивая цель); для нетерминальных блокеров — не раньше **третьего подряд** хода с
  тем же блокером; после возобновления аудит блокеров начинается заново. **[V]**
- При завершении модель пишет **итог или объяснение блокера** в следующем сообщении; рантайм фиксирует событие и
  очищает состояние. **[V]**

## 4. Как обеспечивается автовыполнение

- **Автопродолжение.** По завершении хода, который был «ходом цели», рантайм вызывает `launchContinuationTurn`
  с origin `system_trigger {name:"goal_continuation"}`; ход помечается как goal-driven, считается в бюджет ходов
  (`incrementGoalTurn`, только для «стартового» хода цели). Условия запуска `canLaunchContinuation`: нет живого хода,
  нет отложенного продолжения, петля `idle`, нет ожидающих запросов. **[V]**
- **Аномальные концовки.** `failed/cancelled/blocked` (кроме упора в `max_steps`) → `settleAbnormalTurn`
  (пауза с причиной, продолжения нет). Упор в лимит шагов (`LOOP_MAX_STEPS_EXCEEDED`) не рвёт цель: продолжение
  запускается с флагом `stepCapped`. Отмена пользователем при «возобновлении с продолжением» — продолжение
  перезапускается. **[V]**
- **Паузы с причиной** (`goalFailurePauseReason`): лимит провайдера, ошибка соединения, ошибка авторизации,
  фильтрация, ошибка API, модель не настроена/некорректна, прочие ошибки рантайма. Пользователь возобновляет
  `/goal resume`; вставленные напоминания о заблокированной/приостановленной цели говорят «не преследуется
  автономно, обрабатывай текущий запрос обычно». **[V]**
- **Бюджеты как данные.** `SetGoalBudget { value, unit }`, единицы `turns|tokens|milliseconds|seconds|minutes|hours`;
  ставится только по явному лимиту пользователя («stop after 20 turns», «500k tokens», «30 minutes»), выдумывать
  запрещено; сложное время приводится к одной единице. Жёсткая проверка `blockIfBudgetReached` на старте
  продолжения/возобновления и при установке; причина — строка `GOAL_BUDGET_BLOCK_PREFIX: turn budget …, token budget …,
  wall-clock …`. Для времени — эффект дедлайна (`deadlineDelay/deadlineFired`). **[V]**
- **Возобновление только пользователем**: `active` для paused/blocked — по явной просьбе; внутренние флаги
  `continueIfPaused/continueIfBlocked`. **[V]**
- **Форки**: при форке сессии вставляется напоминание «в этом форке текущей цели нет; игнорируй напоминания об
  активной цели из исходной сессии». **[V]**
- **Телеметрия**: `goal_continued {turns_used}`, `goal_budget_set`, `goal_updated` наружу; состояние цели есть в
  метаданных транскрипта (`goalMeta`: objective, status, completionCriterion, budgetUsed, budgetLimit). **[V]**
- **Долговечность**: события `goal.create {goalId, objective, completionCriterion, time}` и
  `goal.update {status, reason, turnsUsed, tokensUsed, wallClockMs, actor, time}` — часть журнала сессии (в бандле
  видна миграция `wire/migration/v1.4.ts` этих записей); при реплее состояние нормализуется (`normalizeAfterReplay`). **[V]**
- **Старт цели** проходит через режим разрешений (в UI есть `toGoalStartReviewPermissionMode(label)` для
  `auto/yolo/manual`) — запуск автономной работы может требовать подтверждения. Детали UI не разбирал. **[I]**

## 5. Что стоит перенести в Канопус (идеи, не копипаста)

1. **Цель — контракт, а не план**: `objective` + `completionCriterion` в карточке; напоминание «что должно стать
   истинным и как это доказано» каждый ход. У нас `CreateGoal/UpdateGoal` уже близки; стоит добавить явный
   `completionCriterion` и правило «слабое доказательство ≠ done». **[I]**
2. **Долговечные события цели в журнал** (`goal.create/goal.update` с актором и расходом) — восстановление статуса
   после перезапуска без отдельного файла состояния. **[I]**
3. **Автопродолжение отдельным системным триггером** (не «ход пользователя»), с предусловиями «петля свободна,
   живого хода нет, бюджеты не исчерпаны» и флагом «упёрлись в лимит шагов — продолжить». **[I]**
4. **Политика пауз**: единый словарь причин (в т.ч. наш `auth_signal` из 317 — сюда ложится естественно),
   «аномальная концовка → пауза, а не продолжение», возобновление только словом владельца. **[I]**
5. **Бюджеты — данные**: turns/tokens/время, только по явному лимиту, блок-причина в проверяемой строке. **[I]**
6. **Objective как недоверенные данные** (`<untrusted_objective>`) — хорошая форма для наших ворот и напоминаний:
   цель приходит из текста пользователя и не должна перебивать правила/схемы/права. **[I]**
7. **Очередь целей** с автоподъёмом следующей — полезно, когда владелец ставит несколько целей подряд. **[I]**
8. **Напоминание форка**: «в форке цели нет» — прямо применимо к нашей передаче контекста между окнами (298). **[I]**

## 6. Чего у них нет (чтобы не искать)

- Декомпозиции цели на подцели/шаги в рантайме — нет; «план» целиком на модели по одному слайсу за ход. **[I]**
- Проверки критерия приёмки рантаймом — нет: соответствие проверяет модель, рантайм лишь требует «доказательства» и
  фиксирует итог. Автоматического «прогона критерия» не видел. **[I]**
- Множественных одновременных целей у одной сессии — нет: одна текущая + очередь. **[V]**

## Ограничения исследования

- Пакет — **собранный бандл**, не репозиторий: имена функций и тексты видны, но исходная структура модулей —
  только по строкам `//#region ../../packages/...`. Отдельные ветки (UI очереди, режим разрешений старта)
  разобраны поверхностно. **[I]**
- Версия зафиксирована по `package.json` установленного пакета (2.1.1); более новые версии могут отличаться. **[V]**

## 7. TodoList: без дополнительных запросов к модели (дополнение 2026-11-26)

> **Оговорка: TodoList — другой механизм, не цель.** У него нет критерия завершения, бюджетов, статусов и
> автопродолжения; цель — «рантайм гоняет модель до критерия», todo — «модель сама организует себя, рантайм
> только подсвечивает». Раздел лежит в этом файле по принципу «файл = донор», а не потому, что это часть
> механизма целей.

Повод: владелец спросил, делает ли Kimi Code дополнительные запросы к модели для автоматического планирования
todo. Ответ: **нет** — todo-лист целиком инструмент основной модели, плюс механические напоминания без LLM.
Ссылки — на бандл `dist/main.mjs` того же пакета 2.1.1 и исходные пути из его `//#region`.

- **Инструмент `TodoList`** — описание `todo-list.md?raw` (`dist/main.mjs:275468`, исходник
  `packages/agent-core-v2/src/features/todo/tools/todo-list/todo-list.md`). Ключевое дословно: «Use this tool to
  maintain a structured TODO list… **Use it proactively and often**», «mark exactly one item as `in_progress`»,
  «Immediately after finishing a tracked task, mark it `done`; do not batch completions», «Never mark a task
  `done` if tests are failing, implementation is partial». Схема (`dist/main.mjs:275461`): `{ todos?: [{ title,
  status: pending|in_progress|done }] }`; вызов без `todos` — чтение, `todos: []` — очистка, вызов полностью
  заменяет список. **[V]**
- **При вызове** (`dist/main.mjs:275488`): значение пишется в `AgentTodoService`, тот диспатчит durable-событие
  сессии `ToolsUpdateStore { key: "todo", value }` (`todoService.ts`, `dist/main.mjs:264851`) — список
  персистируется в журнале сессии, не отдельным файлом. В вывод инструмента дописывается напоминание
  (`todo-list-write-reminder.md`, `dist/main.mjs:275481`): «Ensure that you continue to use the todo list… keep
  exactly one task in_progress». **[V]**
- **Отдельных LLM-запросов для планирования нет**: ни предзапроса, ни авто-генерации todo из задачи, ни скрытого
  planner-вызова вокруг TodoList. Список создаётся, только когда основная модель сама вызывает инструмент; стимул
  — описание инструмента и напоминания. В основном системном промпте упоминаний TodoList нет. **[V]**
- **Механическое напоминание вместо запроса** (`todoListReminder.ts`, `dist/main.mjs:264712`): если TodoList
  активен, использовался хотя бы раз и с последней записи прошло ≥10 ходов ассистента (и ≥10 ходов с прошлого
  напоминания; константы `TODO_LIST_REMINDER_TURNS_SINCE_WRITE = 10`,
  `TODO_LIST_REMINDER_TURNS_BETWEEN_REMINDERS = 10`, `dist/main.mjs:264768`), в контекст впрыскивается сообщение
  `origin.kind: "injection"`, `variant: "todo_list_reminder"` — дословно: «The TodoList tool has not been updated
  recently… This is a gentle reminder; ignore it if not applicable. Make sure that you NEVER mention this
  reminder to the user» — с текущим списком. Только для main-агента (`dist/main.mjs:264811`), чисто шаблонная
  логика. **[V]**
- **Plan mode отдельно**: инструменты `EnterPlanMode`/`ExitPlanMode` (`dist/main.mjs:205141`) и read-only
  субагент-профиль `plan` (`dist/main.mjs:205119`) — opt-in по инициативе модели или флага сессии, не
  автоматический предзапрос; в plan mode todo не ведётся («in plan mode, write the plan to the plan file rather
  than tracking it here»). **[V]**
- **Персистентность и отображение**: состояние восстанавливается при возобновлении сессии (`dist/main.mjs:264830`);
  при компакции `postProcessSummary` (`dist/main.mjs:265594`) дописывает к сводке секцию `## TODO List` с текущим
  списком — todo переживает компакцию. TUI рисует панель (`dist/main.mjs:480089`, авто-очистка когда все `done` —
  `:478055`); в ACP display-блок TodoList транслируется в `plan` session update (`dist/main.mjs:310356`) — из
  него оркестраторы (bb) рисуют карточку «N/M complete». TodoList — в списке инструментов, авто-одобряемых без
  подтверждения (`DEFAULT_APPROVE_TOOLS`, `dist/main.mjs:273256`). **[V]**

**Вывод для Канопуса [I]:** «автоматичность» todo — дисциплина описания инструмента + шаблонный nudge раз в ~10
ходов + durable-событие + выживание через компакцию. Ноль дополнительных обращений к модели; повторить дёшево.
