# Как Claude Code работает с целями: постановка, шаги, критерий приёмки, автозапуск (исследование 2026-11-21)

Раздел «что перенести» отобран по критериям [doc/research/README.md](README.md).

Повод: владелец спросил, как устроены «цели» в Claude Code и что из этого стоит перенести в Канопус.
Источник — **установленный пакет** `@anthropic-ai/claude-code` версии **2.1.287** (нативный `claude.exe`,
собранный бандл от 2026-10-02): поведение восстановлено по строкам и встроенному JS в бинарнике, плюс
`sdk-tools.d.ts`. Исходники закрыты, поэтому путь:строку к открытому файлу дать нельзя — все пометки **[V]** означают
«проверено по строкам бандла», **[I]** — вывод.

## Главное

- Цель Claude Code — это **условие завершения сессии** («goal condition»): одна фраза с проверяемым конечным
  состоянием и способом проверки (например, «bun test exits 0»). Одна активная цель на сессию. **[V]**
- Цель ставит **пользователь** командой `/goal <condition>` либо модель через инструмент **`ProposeGoal`** —
  но только с одобрения пользователя в одно нажатие (по умолчанию). **[V]**
- После каждого хода отдельный **evaluator** (Stop-hook, отдельный модельный запрос) читает **только транскрипт**
  и выносит вердикт `{ok, reason, impossible?}`. Пока `ok=false`, Claude получает продолжение и работает дальше. **[V]**
- Evaluator **не может запускать команды и читать файлы** — поэтому условие обязано быть доказуемым по разговору;
  «доказательств в транскрипте нет» — это `ok=false`. **[V]**
- Автопродолжение держат: Stop-hook после хода, «check-in» по простою, повторные попытки с паузой при сбоях,
  отдельные паузы с причиной (таймаут проверки, лимиты, ошибка API). **[V]**

## 1. Когда ставится цель

- Пользователь: `/goal <condition>` — условие ограничено по длине («Goal condition is limited to N characters»);
  `/goal active` — показать текущую цель с номером итерации; `/goal clear` — снять досрочно. **[V]**
- Модель: инструмент `ProposeGoal` — «Propose a session goal condition, with one-keypress user approval; once set,
  Claude keeps working until a separate evaluator confirms it is met». Ограничение — 500 символов; неблокирующий:
  предложение висит рядом, работа продолжается; после одобрения — «kickoff message», и только тогда цель активна. **[V]**
- Политика `ask_user`: по умолчанию `true` (диалог); `false` ставить цель без диалога разрешено **только если слова
  самого пользователя в этом разговоре называют этот исход**; при сомнении — спрашивать; отказ пользователя не
  переспрашивать и не предлагать переформулировку. **[V]**
- Где цель недоступна: plan-режим («propose the goal after the plan is approved»), подагенты («cannot be used in
  agent contexts»), неинтерактивные сессии, недоверенный workspace («only available in trusted workspaces»),
  режим ограниченных хуков (`disableAllHooks`/`allowManagedHooksOnly`). **[V]**
- Настройка `modelProposedGoals`: `auto` (по умолчанию; `ask_user` решает модель), `alwaysAsk`, `disabled`
  («Claude-proposed goals» можно выключить). Набранный вручную `/goal` от настройки не зависит. **[V]**
- Одновременно активна одна цель: одобрение нового предложения **заменяет** текущую; повторное предложение при
  уже висящем — не создаётся («A goal proposal is already awaiting the user's decision»). **[V]**

## 2. Шаги и «план»

- Отдельного плана у цели нет. Условие — это **измеримое конечное состояние с проверкой**, и оно же служит
  критерием: «state one measurable end state with its check… evaluator verifies the condition from the conversation
  alone». **[V]**
- Текущие шаги держат обычные механизмы сессии (план-режим, todo, фоновые задачи), а цель лишь удерживает работу:
  после каждого хода evaluator решает, достигнуто ли условие. **[I]**
- Проверка обязана быть видимой: evaluator не запускает инструменты, поэтому «тесты прошли» должно быть в
  транскрипте; при усечении контекста вставляет пометку «Earlier conversation truncated to fit the hook evaluator's
  context window» и оценивает по оставшемуся. **[V]**
- Если ход закончился без оценки — приходит «репромпт»: «Goal check-in: continuing after the last turn ended early:
  `<причина>`. Continue toward the goal»; если в этот момент что-то стоит в очереди у пользователя — репромпт не
  вставляется. **[V]**

## 3. Критерий приёмки

- Вердикт evaluator’а строгий JSON: `{"ok": true, "reason": "…evidence…"}` / `{"ok": false, "reason": "…"}` /
  `{"ok": false, "impossible": true, "reason": "…"}`. Обязательно цитировать места транскрипта. **[V]**
- Формулировка оценки: «insufficient evidence in transcript» → `ok=false`; `impossible` — только когда условие
  действительно невыполнимо в этой сессии (противоречие, недоступный ресурс, исчерпаны разумные подходы);
  «assistant claiming the goal is impossible is evidence, not proof» — evaluator обязан проверить сам; при
  сомнении — `{"ok": false}` без `impossible`. **[V]**
- Изменения статуса наружу идут одним событием `active_goal`: «met» очищает цель, «not-yet-met» увеличивает
  счётчик итераций и `last_reason`; UI с индикатором цели перерисовывается от этого события. Терминальные
  состояния в карточке: «Goal achieved», «Goal could not be achieved», «Goal not yet met… continuing». **[V]**
- У evaluator’а есть таймаут (по умолчанию 30 с) и усечение промпта («evaluator prompt too long; retrying»); при
  неполной оценке — пауза с причиной, а не тихий успех. **[V]**

## 4. Автозапуск и жизненный цикл

- `/goal` регистрирует **Stop-hook** (в UI так и видно: «Session hooks created by /goal, agents and skills still
  run»). После каждого хода Stop-hook запускает evaluator; `not-yet-met` поднимает итерацию и вводит следующий ход. **[V]**
- **Паузы с причиной** (пользователь видит сообщение и продолжает одним сообщением):
  - «the last turn could not finish», «the goal check timed out», «goal checks kept finding it unmet this turn»,
    «a hook ended the turn»;
  - «the request was rate limited» → «send a message to retry»;
  - «usage limit reached» → «continues automatically when it resets». **[V]**
- **Повторы с выдержкой**: при сбое цель остаётся активной — «Goal still active · cause · retrying in N min (m/N) ·
  send a message to retry now», с растущей задержкой; после исчерпания — «Goal paused after N automatic retries». **[V]**
- **Check-in по простою**: если работа встала, через интервал (`CLAUDE_CODE_GOAL_CHECKIN_MINUTES`) вставляется
  «Goal check-in: continuing…»; при работающих фоновых задачах проверка **откладывается**, а затем приходит с
  разными формулировками: «background work still running — check progress; if progressing keep waiting; if stuck,
  fix or stop and continue» или «background work no longer running — it finished or was stopped without reporting
  back. Continue toward the goal». У «простойных» check-in’ов есть **потолок** («[goal] idle check-in cap reached»). **[V]**
- **Пользователь может прервать**: Ctrl+C/Stop → «Goal paused · send a message to continue, or run /goal clear»;
  следующее сообщение пользователя возобновляет цель. **[V]**
- **Неразрешимый сбой**: «Goal cleared after an unrecoverable error. Run /goal again to continue» — цель снимается,
  чтобы не крутиться вслепую. **[V]**
- **Смена цели**: новое `/goal` или одобренное предложение заменяет текущую; «already in goal state» — повторная
  постановка того же условия блокируется. **[V]**
- **Восстановление**: `restoreGoalFromTranscript`, `seedActiveGoal`, «/goal restored on resume» — цель переживает
  перезапуск и подхватывается при резюме сессии; удалённые/облачные сессии умеют «adopt» активную цель. **[V]**

## 5. Что стоит перенести в Канопус (идеи)

1. **Критерий — одна проверяемая фраза с явной командой проверки** (≤500 симв.), а не размытое «сделай хорошо»:
   это дисциплинирует и постановщика, и исполнителя. **[I]**
2. **Отдельный evaluator как Stop-hook**: после хода — короткий запрос «оцени по транскрипту», вердикт — данные
   `{ok, reason, impossible?}`, с цитированием доказательств. Стоит рассматривать даже без режима «цели» — как
   стоп-крючок. **[I]**
3. **Ограничение роли судьи**: он не читает файлы и не запускает команды; «недоказано в разговоре = не сделано» —
   простой и честный контракт. **[I]**
4. **Политика `ask_user`**: модель предлагает цель, но по умолчанию спрашивает; ставить без согласия можно только
   когда слова пользователя прямо называют исход. **[I]**
5. **Итерации и `last_reason`** как метрика прогресса; UI живёт от одного события `active_goal`. **[I]**
6. **Паузы с причиной + выдержка повторов**: не тихое зависание, а видимое «paused, retry in N min» с
   auto-продолжением после лимита. Перекликается с нашими критериями 317/320 «не молчать». **[I]**
7. **Check-in-ы по простою с учётом фоновой работы** («проверь, продвигаются ли, не перезапускай») и с потолком
   простых check-in’ов — антидот от «тихий простой» и от бесконечных кругов. **[I]**
8. **Жёсткие ворота места**: plan-режим, подагенты, неинтерактив, недоверенный workspace — цель там не ставится. **[I]**

## 6. Отличия от Kimi Code, Codex и ZCode

- Claude Code: условие — **короткая проверяемая фраза**, evaluator видит **только транскрипт**; у ZCode судья —
  отдельный модельный запрос с теми же ограничениями, но условие шире; у Codex/Kimi — аудит в тексте продолжения. **[I]**
- Только у Claude Code встретил явный **`impossible`-вердикт** и отдельное «Goal could not be achieved». **[V]**
- Только у Claude Code — **механизм check-in по простою** с учётом фоновых задач и потолком. **[V]**
- Общее: одна активная цель, автопродолжение отдельным ходом, objective/условие как недоверенные данные,
  «слабое доказательство ≠ сделано», продолжение/пауза управляются пользователем. **[V]**

## Ограничения исследования

- Источник — **собранный проприетарный бинарник** (JS внутри нативного exe): тексты и имена символов видны, точные
  структуры и порядок вызовов можно восстановить лишь частично; официальной документации по внутренним правилам нет. **[I]**
- Версия зафиксирована по `package.json` (2.1.287); в новых версиях имена/пороги могут отличаться. Числовые
  значения (минуты check-in, лимит итераций «m/N») берутся из строк/дефолтов бандла и требуют проверки на живой
  сборке, если на них будем опираться. **[I]**
