- 2026-11-28, владелец через интегратора в чате задачи — «везде малый путь». Интегратор поручил совместно проверить задачи 324 и 332 с транспортом 329 и разрешил отдельную ветку от интеграционной. Сохранённые идентификаторы оборванных RPC позволяют отбрасывать повторные ответы.

- Повторный прогон на собранных бинарниках подтвердил все шесть режимов и `src/daemon/local_test.py`. После исправления ссылки тестовой оснастки с `doc/routes` на `docs/routes` сквозной прогон 332 прошёл 4 из 4.

## Этап 2

- Владелец, 2026-11-28, чат этапа 2: «по демону доведи все этапы в автоматическом режиме по рекомендациям».

- Хаб принимает список демонов, хранит ключи по ID, передаёт выбранный ID из новой сессии в журнал и связывает курсор с ID демона и экземпляром агента. Настройка и команды приёмки приведены в [README демона](../../../src/daemon/README.md).
- Nova Oracle 0.1.7 собрала оба бинарника. Локальный транспорт и все шесть режимов хаба этапа 1 прошли. Режим потерянного подтверждения восстановил запись этапа 1 без ID демона.
- Удалённая проба. Хаб выбрал второй ID списка. Блокировка TCP длилась 30,041 с. Тестовый ACP-агент завершился на 0,522 с после начала блокировки. Через 6,062 с после её снятия хаб догнал `seq 3 → 5` и единожды зафиксировал окончание того же хода. В контрольном прогоне немедленный отказ TCP на loopback-транспорте без повторных чтений прервал исходный ход.

- Клиент из отдельного сетевого пространства прошёл WireGuard-туннель. Демон отклонил неверный ключ и неверный ID, принял совпавшую пару. Chromium выбрал второй демон в новом чате, передал его ID по WebSocket и получил ответ ACP. Веб-набор прошёл 655 проверок.

## Этап 3

- Владелец, 2026-11-28, чат этапа 3: «по демону доведи все этапы в автоматическом режиме по рекомендациям».
- Запись причины смены ветки. Что — с ветки окна на `task/329-daemon-stage3` в том же дереве на `bab25a50`. Зачем — изолировать этап 3 на опубликованной базе этапа 2. Кто — поручение владельца от 2026-11-28 в чате этапа 3: «Машина selectel, своё дерево от origin/main (после bab25a50 — этап 2 в main), ветка task/329-daemon-stage3».
- Малый маршрут. Выдача и отзыв через HTTP API пульта и окно «Машины». Демон погашает одноразовый ключ на отдельном loopback-порту регистрации, который можно пробросить по SSH. Список выбранной машины строится из того же реестра, что и серверный выбор.
- Исходный прогон новой фикстуры на `bab25a50` остановился на выдаче ключа с HTTP 405. Веб-набор прошёл 655 проверок. Chromium прошёл выдачу ключа, подключение демона, последний контакт, выбор машины и отзыв.
- Локальный транспорт и шесть режимов хаба этапа 1 прошли. Статический демон из бинарника `bab25a50` прошёл восстановление с новым хабом. Удалённое восстановление с недоступной первой машиной прошло в отдельном повторе за 3,043 с. Первому прогону не хватило ответа на следующий ход после восстановления. Проба этапа 2 с разрывом 30,024 с догнала кадры с 3 по 5 и завершила тот же ход через 5,980 с после восстановления сети.
- В наборе Nova для фронта падает `front public config: custom basename and instance folders` на сравнении путей Windows. На неизменённой базе `bab25a50` на Selectel та же проверка падает в той же строке.
- Nova Oracle 0.1.7 собрала `canopus` и `canopus-hub`. Сквозная проверка прошла на loopback и на адресе WireGuard отдельного демона. Проверены TTL, повторная выдача, конкурентное погашение и доставка отзыва после появления демона. Отзыв закрывает ход и останавливает ACP-процесс. При повторном открытии страницы видна причина. После перезапуска демон отклоняет старый ключ.
- Приёмка описана в [README демона](../../../src/daemon/README.md). Федерация и однострочная автоустановка демона на новую машину остаются за границей эпика.
