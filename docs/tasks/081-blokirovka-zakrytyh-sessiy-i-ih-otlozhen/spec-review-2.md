## Находки

1. ### S1 — spawn до устойчивой записи PID и нет восстановления intent/identity; критичность: существенная; уровень: требования

- **Источники:** `opencode-plugin/watch.ts:61–65, 70–76, 103–116, 166–187`; `spec.md:30–32, 46–48, AC-02/05`.
- **Факт:** consumer переименовывает `.req.json` в `.claim`, читает и удаляет claim (179–185), затем вызывает detached `spawn` (103–111), и только после возврата записывает `.json` с `pid` (186). Падение между удалением claim и записью результата оставляет неидентифицированный внешний процесс или потерянное задание; событие `child.error` лишь логируется асинхронно (109). Кросс-процессный rename claim не сериализует close с spawn и не обеспечивает crash recovery. Запись `.tmp`/rename для одной записи не является общей транзакцией с OS spawn.
- **Воспроизведение (ручной сценарий, без запуска):** остановить процесс-хост сразу после успешного `spawn`, до writeAtomic; рестарт увидит ни request, ни claim, ни running record, хотя detached child может существовать. Вход/ожидание перечислены в `session-evidence/s2-2/probe-plan.md`.
- **Почему существенно:** REQ-03 говорит «start выигрывает — close ждёт/видит exact identity», но спецификация не задаёт точку линеаризации, durable intent, recoverable identity при crash или значение «close завершён». Не определён безопасный исход для обязательного окна.
- **Исправление / уровень:** на уровне требований задать подтверждаемую границу завершения close и crash outcomes/наблюдаемость, не предрешая primitive. План обязан доказать поддерживаемое межпроцессное сериализование и восстановления; если платформа не может дать обещание — явный STOP/вопрос владельцу, не молчаливый успех.

2. ### S2 — область гарантий новых ходов смешивает подконтрольные и внешние OpenCode writers; критичность: существенная; уровень: требования

- **Источники:** `spec.md:38–40, 64–68, 83–85`; `opencode-plugin/index.ts:580–641, 2035–2042`; фактический V2 OpenAPI и официальная API-документация.
- **Факт:** `postLetter` (core.ts:1111–1117) — файловый writer без общей проверки lifecycle. `crew_send` (core.ts:1913–2008) может записать explicit-session letter; общий `deliver` (index.ts:295–383) сам не проверяет `spawned.status`, а ряд вызовов входит напрямую (568, 797, 1035, 1376, 1865, 2161), в дополнение к poll loop, где на одном из проходов есть закрытый-card filter (2039–2042). `resumeInterrupted`/`retryFailed` (580–641) читают allCards и obligations, затем `postLetter`; отдельной closed-card проверки в этих ветках не видно. `finishTasks` может переместить watch в новый request (652–672), а `requestWatch` не валидирует старый session lifecycle. OpenCode V2 предоставляет независимые session prompt/command, inbox list/cancel и interrupt маршруты. GET/interrupt/cancel имеют разный смысл; `interrupt` не запрещает будущий prompt, а отмена отдельного inbox item не превращается в durable lifecycle fence. Документация описывает API, но не гарантирует внешнее исключение произвольных клиентов.
- **Воспроизведение:** сценарий 1 — после close вызвать `resumeInterrupted` или `crew_send`/прямой вызов `deliver` для старой card: writer/prompt-путь может оказаться без общей lifecycle gate; сценарий 2 — сторонний клиент напрямую делает V2 prompt или добавляет inbox item. Не отправлялись prompt/command и не вызывались mutations.
- **Почему существенно:** абсолютный REQ-05/AC-04 невозможно доказать только локальными тестами без определения trust boundary/контроля внешнего клиента. Нельзя закрыть словами «план выберет API».
- **Исправление / уровень:** исправить формулировку требования с явным actor/trust boundary: что именно CrewHarness обязуется запретить/проверить, а внешнее состояние — отдельно инспектировать и оставлять UNKNOWN/STOP; либо задать владельца и поддерживаемый механизм запрета на уровне OpenCode. Решение о сокращении обещания — только владелец.

3. ### S3 — выход процесса и изоляция scratch обещаны абсолютнее доступных доказательств; критичность: существенная; уровень: требования

- **Источники:** `spec.md:16–18, 34–36, 42–44, 50–52, AC-03/06`; `watch.ts:93–101, 108–115, 217–229`.
- **Факт:** watch хранит PID, запускает detached child с наследуемым `process.env`, на Windows `dropWatch` вызывает `taskkill /T /F`, ловит ошибку, но всегда пишет `done/code:null` (220–229). Один PID без неизменяемой process identity не защищает от reuse; PID/PPID snapshot не покрывает переподчинённые потомки, открытые handles и writer вне наблюдаемой process tree. AC-06 требует невозможности записи old process в scratch нового worker, но spec не выбирает sandbox/ACL/handle boundary и не может доказать это простым side-effect fixture.
- **Воспроизведение:** kill возвращает ошибку или процесс успевает отделить потомка; запись `done` все равно появляется. Старый процесс с ранее открытым write handle сохраняет возможность записи в каталог нового worker.
- **Почему существенно:** REQ-04/06/08 и AC-03/06 требуют сильнее, чем доказывает `done`, PID-check и успешность команды kill.
- **Исправление / уровень:** требовать фактический outcome/UNKNOWN и уточнить, какая модель угроз входит в scope. План может выбрать поддерживаемую OS isolation primitive; если нет — exact STOP и потребность отдельного решения владельца. Не заявлять универсальную защиту/изоляцию заранее.

4. ### S4 — AC-02 допускает два несовместимых исхода без критерия приёмки; критичность: существенная; уровень: требования

- **Источники:** `spec.md:30–32, AC-02`; `watch.ts:171–187`.
- **Факт:** критерий принимает «close выигрывает — не spawn» ИЛИ «start выигрывает — close ждёт/видит exact running identity и отзывает адресно», но не задаёт победителя для одного фиксированного interleaving, что считается успешным close, максимальное ожидание, поведение при crash до identity и обязательную проверку side effect. Это не просто выбор архитектуры: результат RED→GREEN нельзя бинарно определить.
- **Воспроизведение:** один и тот же тест close concurrent with start может законно закончиться запуском команды после close, а AC допускает это при гипотезе start-wins; нет наблюдаемого oracle для завершившегося close.
- **Почему существенно:** acceptance criterion недетерминирован; автоматизированная проверка может PASS при небезопасном запуске.
- **Исправление / уровень:** определить линейную точку, исход каждого race case и измеримый oracle «после завершённого close нет нового side effect; ранее admitted identity учтена/не доказана => STOP». Конкретный механизм оставить плану.

## Пробы и фактические результаты

1. **Кодовый причинный audit (ручной, вход до проверки записан в `session-evidence/s2-2/probe-plan.md`).** Результат: в `watch.ts:70–76` request создаётся без lifecycle guard; `166–187` claim→remove→spawn→write running не атомарен с close; `217–229` kill failure проглатывается и запись всё равно становится done; точки вызова `core.ts:2092–2104, 2246, 2959–2984, 3167–3207, 3326` и `index.ts:580–685, 805–815, 1880–1888, 2033–2042` разделены по переходам/retry/reconcile/dispatch. Ожиданию общего проверяемого fence не соответствует. Это source audit, не тест.
2. **Контрактная положительная/отрицательная проба (ручная).** Пройдены race close-before-claim, close-after-claim-before-spawn, crash-after-spawn-before-record, kill error/PID reuse, inbox item and external direct prompt, нового worker scratch и повтор после interrupt. Ключевые отрицательные сценарии подтверждают S1–S4; положительный новый worker отдельно сформулирован, но нет runnable isolated fixture/test — поэтому GREEN не заявляю.
3. **Forensic/preservation проба (read-only).** Сырой intake manifest: пересчитано 87/87 сохранённых файлов, сумма 1,804,234 bytes, несоответствий/недоступных файлов нет; dossier 15,150 bytes и SHA-256 совпал с переданной описью. Это только перечисленные существующие копии, не восстановление утраченных run1 архивов/logs. Текущая watch-каталоговая сверка по точной session ID нашла 7 JSON-records, все `done`, без `.req.json`/`.claim`; из восьми записей предыдущего inventory одна старая запись в текущем каталоге отсутствует, при этом шесть заданных run1 IDs и run2 ID присутствуют. Повторный Win32_Process snapshot только PID/PPID/Name/CreationDate, без CommandLine/environment, не нашёл совпадений для восьми записанных PID/PPID. Это моментальный snapshot, не lineage/exit proof/fence. Raw run1 архивы и CMake logs не восстановлены.
4. **V2 API проба.** Официальный OpenCode V2 API guide (версия маршрутов, не V1) и актуальный `/openapi.json` подтверждают GET `/api/session/{sessionID}`, GET `/api/session/{sessionID}/inbox`, POST interrupt и DELETE inbox item как отдельные операции. Штатный CLI запросы GET выполнил с exit 0; metadata response exact ID совпал, поля верхнего уровня ограничены ключами метаданных, inbox count=0. Число/содержимое сообщений/поля `location`, `title`, `model` в публичный отчёт не выведены. Сырые ответы внешне сохранены вне репозитория; в public evidence только байты/SHA/route/exit/метаданные. Это состояние момента чтения, не постоянная блокировка и не просмотр transcript. Никаких mutations не было. До составления `probe-plan.md` была предварительная безопасная попытка через Python `subprocess.run(['opencode', ...])`: exit 1 из-за `FileNotFoundError [WinError 2]` (обёртка не разрешила имя CLI, HTTP запроса не было); маршрут через официальный установленный CLI найден, после плана GET повторён и успешен. Первая ad hoc GET-выборка до плана не засчитывается формальной пробой.
5. **Проверка публичных машинных путей.** До сканирования план требовал ноль локальных Windows-путей в новых текстах и запрещал искать private names/secrets. Первая команда дала один false-positive на буквальный шаблон в первой версии самого плана; ошибка сохранена в `session-evidence/s2-2/public-path-probe-initial-error.md`, шаблон плана исправлен. Повторный scan тех же 18 собственных report/evidence-файлов: вывод `{"files_scanned":18,"machine_path_prefix_hits":[],"private_names_or_values_searched":false}`. Не заменяет полный CI/secret/private-name guards.
