## Две линзы и документальные пробы P1/P2 — фактический ручной результат

Линза согласованности/исполнимости: одна существенная S1, поверхностных 0.
P1: inspected 5 классов (preflight L, always STOP, success+B, обязательные fault points, T/clock). Положительный oracle success+B найден явно в spec98–109/241–245; подстановка always STOP нарушает AC-16. Claim-loss/spawn-before-PID/PID failure/two-consumer не исключаются из L после результата. Временной бюджет и конкретные часы ещё плану; отсутствие нынешней реализации не доказывает невозможность L. Ранняя заметка про неограниченные размеры/справедливость оставлена как инженерный риск: на этом чтении нет доказательства, что ни один допустимый primitive/clock не выполнит контракт, поэтому отдельной существенной находкой не объявлена. План не может молча подменить L/T и обязан вернуться при невозможности.

P2: inspected 8 расписаний из probes.json. Первые 7 имеют заданный outcome: A-source deny; A-recipient deny без B-retarget; B-only allow; bound role deny против independent open request allow; claim до C без D deny; D<C до начала effect — revoke/terminal без нового start; receipt до C — не разрешение, external без terminal unresolved.
Восьмое расписание выявляет S1: O persisted, два consumers конкурируют; C фиксируется раньше D — REQ-03/AC-02 требуют 0 admissions/effects, AC-05 буквально требует ровно1. Положительная B на том же consumer должна получить1. Вторая сторона того же дефекта: spec48–50 требует отдельной effect-записи той же O после mailbox→host boundary, REQ-14 ещё D перед подконтрольным effect; AC-05 не называет отдельную единицу, позволяющую отличить два разрешённых этапа от повтора. Честные реализации: дедуп по O блокирует законный следующий этап; новые D под той же O отвергаются exactly-one oracle. Это один класс несогласованной кратности, не два findings.

Линза обхода/злоупотребления: та же S1 (не двойной общий счёт), поверхностных0. Проверены обходы service sender, quiet/synthetic/final note, persisted до close, stale claim/recovery, silent role-retarget, external input, PID reuse/reparenting/handles, positive B. Новые gates описаны в тексте; гарантии реального продукта не доказаны. Ошибочное понижение scope до локального PASS явно запрещено. Runtime/raw/exit для P1/P2: N/A, ручные трассы по опубликованным строкам, без исполнения продуктовой модели.

## Первичные API/platform и небиндинговое мнение

OpenCode skill загружен до API-разбора; V2 API и plugins Sessions783–860 прочитаны. Фактическая ранее сохранённая schema-selected JSON декодирована: шесть paths, семь применимых method definitions (включая remove); обязательный data не []. Prompt durably admits input; command immediate callback; inbox list только not-yet-delivered; cancel pending-only/noop unavailable; interrupt execution этого процесса, resume:true может продолжить steering/control items. Examples plugins command/continue расходятся с actual schema; не основание admin по памяти. Нового live GET/metadata/inbox не выполнялось и свежего empty inbox не утверждаю.
Microsoft Job Objects содержательный текст полностью прочитан: job membership наследуется обычным CreateProcess, Win32_Process.Create/breakaway отдельны; не все completion messages гарантированы; last-handle KILL_ON_JOB_CLOSE и named open существуют, но security на каждом процессе. UpdateProcThreadAttribute HANDLE_LIST/SECURITY_CAPABILITIES/JOB_LIST прочитаны адресно, не весь Win32 справочник. Node child_process detached1212–1224 и kill/killed/PID1756–1826 прочитаны. Ни одна страница не доказывает собранную комбинацию L или права B; это основания будущего исследования, не план и не feasibility PASS.
В-01: независимо рекомендую сохранять global HOLD до внешнего/legacy terminal proof; локальный C не отзывает durable host input. Сужение цели — только владелец, не моя поправка.
В-02: независимо рекомендую отложить admin до утверждённого плана и безопасного exact scope proof; snapshots8→6→5 и cancelled/done недостаточны. Даже утверждение этого текста не разрешит mutation.
Это мнение новой С2-5, не prior opinion автора и не ответ на В-01/02. Sol/OpenAI совпадает с семьёй автора по явному разовому решению владельца. Новый peer запрещён; нет приписанного согласия Kimi/второго агента. Оба предметных вопроса не отвечены.
