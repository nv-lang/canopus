# Анализ С1-2 — блокировка закрытых сессий

## Итог

**STOP по административному действию и HOLD для Nova #94, не STOP всей С1.** Читаемая часть расследования завершена. Текущая реализация содержит проверяемый путь, объясняющий класс дефекта: при reassign `releaseExecutor` ставит `spawned.status = "closed"` и снимает obligation, но не отзывает отложенные watch и не прерывает ход; `crew_watch`/`crew_timer` после `host.touch` вызывают `requestWatch` без проверки закрытого статуса; фоновый `pollWatches` захватывает `.req.json` атомарным rename и запускает detached-процесс без повторной проверки жизненного цикла сессии. Долговременного fence в этой версии кода не обнаружено.

Это вывод из локальных исходников, не доказательство конкретной последовательности инцидента и не подтверждение отсутствия будущего запуска. Восемь исторических watch old session сейчас имеют `done` и записанный exit code 0; свежий ограниченный process snapshot не нашёл совпадений PID/PPID. Внешний read-only API-запрос сессии/inbox был прерван перезапуском сервера до результата. Поэтому нельзя утверждать отсутствие pending inbox, всех потомков либо постоянного fence; реальный `#94` не запускался, watches не отменялись.

- **F5 — границы процесса.** Это один моментальный снимок. PPID не покрывает потомка, который был переподчинён/отсоединён; process status не доказывает, что PID не успел переиспользоваться вне сверяемого creation identity; будущий request этим не предотвращён. Командная строка и environment не читались, полный env dump/credentials не собирались.
- **F6 — reassign.** В `core.ts` `startSession` помечает прежнюю запись задачи `handed`, затем вызывает `releaseExecutor`; эта функция закрывает card `spawned.status` и снимает obligation, но не касается файлов watches или OpenCode ходов. Сам `reassign` после этого создаёт новую сессию и запускает её через `host.startTask`.
- **F7 — постановка/запуск watch.** `crew_watch` и `crew_timer` получают card через `host.touch`, но не проверяют `spawned.status === "closed"`; оба вызывают `requestWatch`. `requestWatch` атомарно пишет `.req.json`. `pollWatches` при проходе переименовывает request в `.claim`, удаляет claim и вызывает detached `start`, после чего пишет `.json` со статусом `running`; проверки статуса владельца между claim и start нет. Старт дочернего процесса отделён от записи watch-файла и от другого прохода/экземпляра плагина.
- **F8 — отмена/exit.** `cancelWatch` доступна только владельцу watch. `dropWatch` удаляет queued request или вызывает `taskkill /T /F`, ловит ошибку, затем всё равно записывает `done`, `code: null`, `dropped: true`. Ни запись `done`, ни ошибка остановки не являются доказательством фактического выхода процесса. В штатном poll наличие `.exit` или отсутствие PID после 10 секунд может дать `done`; только подтверждённая идентичность и наблюдение завершения достаточны для строгой доказательной процедуры.
- **F9 — end-task/recovery.** `finishTasks` отдельно переносит watch из дерева закрытой задачи в project directory (снимает старый процесс, ставит новый request) и снимает open watches у завершённых задач; эти ветви не являются session-lifecycle fence на каждом старте. `resumeInterrupted` восстанавливает прерванный ход по obligations; handoff очищает task obligation, но общего запрета нового хода для закрытой spawned-card в рассмотренной части нет. Reconcile ориентирован на актуальные open tasks и журнал, не делает атомарную сверку card lifecycle с watch claim/start.
- **F10 — OpenCode V2 schema.** `opencode api get /openapi.json` успешно вернул фактическую схему сервера. Найдены GET session inbox (`session.inbox.list`), DELETE конкретного inbox item (`session.inbox.cancel`), POST interrupt (`session.interrupt`) и POST prompt/command для новых ходов. Это разные операции; DELETE/interrupt mutation в С1 не вызывались. Последующий read-only GET конкретной старой session и inbox был прерван сигналом перезапуска сервера; ответа/статуса нет. API state поэтому UNKNOWN. OpenCode skill предписывает считать актуальный V2 OpenAPI источником истины.

## Выводы (INFERENCE)

- **I1.** `CLOSED` в CrewHarness сейчас — состояние карточки/задачи и фильтр некоторых адресных путей, а не неизменяемая граница полномочий. Уже поставленный watch хранит независимую session string и переживает ход и рестарт; закрытие card само по себе его не revoke.
- **I2.** Один лишь `interrupt` текущего OpenCode хода не отзывает detached watch, не удаляет queued inbox input и не запрещает будущие prompt/ходы. Отмена watch также не обеспечивает fencing новых request без проверки статуса при постановке и атомарной claim/start.
- **I3.** Корректный механизм должен быть целостной state transition с монотонным lifecycle epoch/generation или equivalent tombstone, используемой всеми writers и consumers, плюс serialized claim/start и exact owner binding. Иначе race close-after-check, restart, несколько плагинов/процессов и идемпотентный retry оставляют окно исполнения.
- **I4.** `#94` нельзя разблокировать по нулевому snapshot: закрытая сессия может получить новый ход, а API состояния не прочитан. Безопасное выполнение адресных revoke/stop отдельно требует одобренного протокола и proof фактического exit; текущая С1 его не исполняла.

## Неизвестное / STOP

- **U1 — текущие session/inbox данные.** GET session и GET inbox были начаты через штатный V2 API-клиент, но вызов завершился `aborted` при перезапуске сервера. Неполученные ответы не интерпретировать как пустой inbox. Прочитать в следующей разрешённой возможности без prompt/mutation.
- **U2 — полная process lineage.** Нет доказательства отсутствия detached/reparented descendants или неизвестных потомков; нет durable PID identity handle, который можно безопасно остановить одной командой.
- **U3 — exact incident chronology.** Предоставленные копии подтверждают состав/хеши и записанные статусы, но run1 raw logs утрачены, а текущий доступный материал не доказывает, какой конкретный источник перезаписал какие байты в точной последовательности.
- **U4 — реализация.** Не выяснялись все cross-process locking/atomicity свойства на поддерживаемых файловых системах и права на OpenCode mutations. Не обещать гарантию до плана/реализации и RED→GREEN.
- **STOP.** Не вызывать cancel/delete/interrupt/taskkill и не запускать старую сессию. Требуется продолжение read-only API inspection и последующая спецификация/ворота; #94 остаётся HOLD.
