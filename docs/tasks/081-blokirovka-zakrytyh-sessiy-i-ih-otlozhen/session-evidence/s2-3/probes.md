# Свои пробы С2-3

План/ожидаемое записаны до выполнения каждой пробы; только чтение. Ни одна проба не запускает продуктовую команду и не является GREEN работающей реализации.

1. **Контрактный причинный проход.** Вход до сверки: фиксированный порядок close-before-admission и admission-before-close; crash после spawn до PID persistence; потерянный intent; два poller/retry; close повторно. Ожидаемо: ровно один исход на каждый порядок, crash не может привести к успешному close без exact terminal evidence. Метод: вручную сопоставить REQ-01/03/04/10 и AC-01/02/04/05 с фактическими `watch.ts` переходами и терминологией spec. Факт: REQ/AC формулируют единственные исходы и запрет success на UNKNOWN; не определяют исполнимый terminal proof/достижимый Green для всех поддерживаемых случаев. Проба текстовая, не тест.
2. **Ownership/source-recipient.** Вход до сверки: закрыт старый исполнитель A; A может обратиться к writer, B — replacement; direct delivery/letter может иметь A источником или получателем, роль-очередь разрешается позднее. Ожидаемо: запрет определяется exact identity/generation и не блокирует B; ни stale source, ни closed recipient не получают неявного исключения. Метод: сравнить REQ-05/08 и AC-03/08 с `postLetter`, direct `deliver`, `crew_send`, recovery/retry и role queue. Факт: spec требует закрывать все локальные пути и отдельно разрешает replacement, но не задаёт наблюдаемую проверку обеих сторон (source и recipient) и поведения уже queued message; вопрос ownership оставлен плану без однозначного oracle в spec.
3. **Forensic preservation/digest.** До вызова ожидалось 87 копий / 1,804,234 bytes / zero missing, dossier 15,150 bytes и digest из первичного intake `7a1f831a85caa227d9d3c36c45f6bf34bab144ea29e1080b58607ed8825d9969`. Метод: hash только сохранённые файлы по basename из исходного raw manifest; исходники не открывались как payload и не изменялись. Actual: 87/87 точных bytes/hash, 0 missing/ambiguous, 0 mismatch; сумма 1,804,234; dossier actual совпал с expected. Утрата run1 archives/CMake logs остаётся отдельной, не восстановленной.
4. **Точная текущая inventory + API.** Ожидание до вызова: отбирать только `session==oldID`; replacement IDs не приписывать; никаких inbox bodies, transcript, environment или mutation. Метод: enumerate records `*.json`, затем read-only `Win32_Process` по записанным PID/PPID без CommandLine; штатный `opencode api` GET `/openapi.json`, session и inbox; проверять exact ID после unwrap `data`. Actual: текущий каталог содержит 5 old records из восьми исторических: все `done`, PID 56580, 84596, 52844, 66548, 81232; исторические IDs `1792179830027-y3slcn`, `1792183468927-mmg9gt`, `1792187099073-itfcuj` в текущем каталоге не найдены, причина отсутствия UNKNOWN. Наблюдались также отдельные replacement records, не включённые в old inventory. CIM не вернул ни один из пяти PID. API вернул exact session ID; status field отсутствовал/не распознан и не заявляется; inbox распознан как пустой массив, count 0. Это снимок, не exit proof/fence. Первый CLI вызов прерван инструментом; первый JSON parse завершился ошибкой BOM (code 1); повторный OpenAPI parse и адресные GET успешны. Не заявляется, что первоначальная попытка была API отказом.
