# Разбор задачи 146

## Краткий разбор

Наблюдение пока ограничено synthetic performance fixture `crew-progress.test.mjs`, AC-11 б. Она измеряет cold `createScanner().scanAll()` над 20 журналами с суммарно примерно 12 тыс. строк и plain `readFileSync` тех же файлов; `scanAll` строит новый scanner на каждой из 20 cold-проб. Условие исходное: `cold.med <= 4 * read.med && cold.p90 <= 6 * read.med`, где `read.med` — медиана plain-read выборки. Это сравнение synthetic workloads, не продуктовый SLA.

Данные 136 подтверждают 3/10 красных повторов `crew-progress`; все красные — только p90-ветка, медианная ветка проходила. Две прежние попытки полного набора 136 остановились на той же проверке; изолированный одиночный прогон проходил. Однако green-метрики не сохранены, CPU/global load не собраны, и поэтому нельзя определить частоту/распределение хвоста у прошедших запусков или приписать причину машине.

Есть установленный недостаток доказательной методики: общий helper `measured()` повторяет полный набор до первого успешного результата (до 3 попыток), что может скрыть красные серии, а не фиксировать каждую пробу. Для AC-11 б при каждом повторе снова измеряется выборка из 20 пар, но наружу выводится только итоговая выборка и только красные метрики сохраняет `stable.mjs`. Внутри каждой пары cold идёт перед read; пары не рандомизированы. Эти факты делают гипотезу смещения/потери данных правдоподобной, но пока не доказывают, что именно они вызвали 3/10 FAIL или что scanner не замедлился.

В `progress-scan.ts` cold путь перечисляет деревья и каталоги, сортирует изменённые журналы, читает каждый через `readStamped` (open + два fstat + read + проверка стабильности), разбирает UTF-8/строки, затем строит tasks. Fixture сравнивает его с одним только чтением; различие этих операций — часть тестируемой стоимости, не равенство операций. Сверка `eb0cec8..2307f69` показывает отсутствие изменений в `progress-scan.ts`, `progress.ts`, `crew-progress.test.mjs` и `stable.mjs`. Сверка source `2307f69..fff980e` показывает, что scanner и perf fixture также не изменены; candidate меняет только статический `TASK_WORDS` mapping в `progress.ts` (`done`→`completed`, новый `closed`). Значение инициализируется импортом вне измерительных циклов, поэтому по коду это изменение не меняет работу замеряемого scan/parse пути. Git blob hash `progress-scan.ts` одинаковый на base/source/candidate/current: `d29cf9a36ae58f6e12ed45450fc2b566e9d5f3b5`; исходный `crew-progress.test.mjs` тоже одинаковый: `d1763b718e3c3d313f0d6691fadddbddfa6fb3eb`. Это доказательство отсутствия изменения целевого пути между этими SHA, не объяснение межзапускового хвоста: lifecycle изменения в других файлах всё же присутствовали в candidate и запрещены к переносу в 146. Текущая задача основана на `origin/main` после fetch: `169abc008cf6a42c8acc447a39987b41974b34df`.

Запрещены увеличенные пороги ради PASS, снятие assertion/теста, retry-until-PASS и изменение 136/140/145 ownership/lifecycle/verdict. ## Предварительно зафиксированный план диагностических измерений (до запуска)

Запускать только после явного подтверждения очередности интегратором с учётом 145; каждый повторяемый запуск — `crew_watch` с `machine: true`, без параллельных дублей. Это не утверждение об эксклюзивной машине: локальный `machine_slots=2`, возможны внешние OS/проекты.

1. **Контроль baseline/current:** текущая ветка `origin/main` SHA `169abc008cf6a42c8acc447a39987b41974b34df`; после instrumentation — отдельная последовательная команда десять раз запускает `node test/crew-progress.test.mjs` (не `stable.mjs`, который теряет stdout успешных детей). Сохраняем legacy test semantics на диагностическом baseline; на каждый из до 3 внутренних попыток AC-11 б выводим все 20 cold/read значений, med/p90, исходную формулу и PASS/FAIL, wall-time, Node/OS/env allowlist, `process.cpuUsage()` delta, `os.loadavg()`, число logical CPUs. Отчёт включает каждую попытку без исключения или выбора «лучшей»; поведение helper отдельно оценивается после получения baseline data. Остальные клетки теста сохраняют исходное поведение. Не исключать красные пробы. Не изменять OS settings.
2. **Сопоставимый candidate:** так как scanner и perf fixture не изменены между base/source/candidate 136, сравнить только read-only target files/тестовые хэши и проверить mapping path usage; не запускать чужое lifecycle-кандидатное дерево и не переносить его diff. Одинаковый target code предсказывает отсутствие различия; различие результатов будет измерительной/нагрузочной вариацией, не доказательством регресса.

**Точность интерпретации:** p90 текущей реализации для 20 наблюдений берётся как отсортированный элемент с индексом `floor(20*0.9)=18` (19-е значение, то есть эмпирически ближайший верхний хвост, не классическая интерполяция). Сравниваем ровно исходные gates `med <= 4*read.med`, `p90 <= 6*read.med`; изменение этих критериев этим планом не разрешается.
