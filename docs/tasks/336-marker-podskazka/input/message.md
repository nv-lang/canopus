# 336. Маркер-подсказка следующего сообщения

## Чего хочет владелец

Владелец, 2026-11-28 («да»): владелец жмёт чип вместо набора текста. Без дополнительных LLM-запросов — агент эмитит маркер в том же ответе. Улучшено вторым мнением (gpt-6.1-sol, 2026-11-28).

## Формат маркера

```
:canopus-next[ярлык]{prompt="JSON-строка"}
```

`prompt` — JSON-строка: кавычки `\"`, перенос `\n`, обратная косая `\`. Символ `}` внутри строки экранировать не нужно — парсер учитывает кавычки, не ищет первую `}`.

## Что нужно

- **Парсинг после завершения хода** (не при стриминге). Незавершённый или битый маркер остаётся обычным текстом, без чипа.
- Распознавание **только в тексте ответа агента**, вне блоков кода и inline-кода. Журнал хранит оригинал без изменений; маркер вырезается только из показа.
- Несколько маркеров = несколько чипов (альтернативные ответы). Каждый чип отправляет свой `prompt` как `user_message`. После выбора остальные чипы этого хода неактивны.
- Двойной клик и повторная доставка не отправляют дважды (дедуп по сессии+ходу). После нового хода старые чипы отключаются.
- Чип — предложение текста, не подтверждение вопроса и не разрешение действия. Существующие ворота владельца не обходятся.
- Инструкция агенту — в системном промпте хаба (формат + правило «от лица пользователя, с учётом принятых решений»).

Красные тесты: маркер → чип, не виден в тексте; нажатие шлёт точный prompt; два маркера — два чипа, выбор гасит остальные; битый маркер молча текстом; маркер в блоке кода не распознаётся; разрыв маркера на каждой границе чанков (стриминг); кавычки, `}`, переносы, Unicode в prompt; двойной клик — одно сообщение; устаревший чип неактивен; старые журналы без маркеров — как прежде.

## Границы

Не генерируем подсказку отдельным запросом. Не храним маркеры отдельно. Агент не обязан эмитить. Стиль — technical-writing.md.
