# Философия Канопуса

## Канопус отвечает за задачу до её закрытия

Владелец задаёт ожидаемый результат. Канопус должен довести задачу до этого результата и проверить его по согласованным условиям приёмки. Для задач разработки цель — выпустить изменение в рабочую среду. Владелец пока не определил, когда для закрытия задачи достаточно проверенного исправления в ветке. [Открытый вопрос 12](../open-questions.md#12-условие-закрытия-задачи)

Настройки проекта определяют, кто выбирает модель — пользователь или Канопус. На любом шаге Канопус должен позволять сменить модель или семейство агентов в той же сессии. Следующий ответ должен появиться в том же диалоге.

При смене исполнителя Канопус сохраняет идентификатор сессии. Любая ранее выданная ссылка на сессию открывает тот же диалог со всей историей переписки, сколько бы раз ни менялся исполнитель.

После смены исполнителя Канопус должен продолжить ту же задачу с учётом её цели, принятых решений и подтверждённых результатов. Порядок работы и условия приёмки остаются общими для всех моделей. [ADR-0018](decisions/ADR-0018-process-in-canopus.md)

Если один путь закрыт, Канопус должен выбрать самый быстрый из доступных путей к тому же результату в пределах полномочий проекта. Если продолжить работу нельзя, Канопус должен сообщить, что мешает и какое решение или событие позволит продолжить.

Если для задачи установлен бюджет, Канопус должен учитывать расход по всем исполнителям и попыткам. При смене модели уже потраченные ресурсы входят в тот же бюджет. Если ни один допустимый путь не укладывается в остаток, Канопус должен приостановить задачу, сохранить её состояние и показать владельцу лимит и расход.

«Поставил задачу — и забыл». Если агент перестал отвечать, приходится ли владельцу самому замечать сбой и возобновлять работу?

## Журнал хранит состояние задачи

Канопус засчитывает выполнение шага по событиям в журнале задачи. После перезапуска или смены агента Канопус должен восстановить по журналу, какие шаги завершены и на каком шаге продолжить работу. [ADR-0018](decisions/ADR-0018-process-in-canopus.md)

## Каждое ожидание видно в интерфейсе и ограничено по времени

Пока сессия ждёт, Канопус должен показывать причину ожидания в списке сессий. В открытом диалоге пользователь должен видеть, когда началось ожидание и требуется ли от него действие. Если причина неизвестна, Канопус должен показать последнее подтверждённое событие и сколько времени с него прошло. Когда причина меняется или ожидание заканчивается, Канопус должен обновить статус автоматически.

Когда Канопус ждёт ответа агента, сервера или дочернего процесса, он должен ограничить время ожидания. Если у запущенного процесса нет собственного механизма остановки по сроку, Канопус должен назначить ему сторожа. Сторож следит за признаками работы и останавливает зависший процесс. Если срок ожидания истёк, Канопус должен показать владельцу причину остановки и записать в журнал последнее событие и длительность ожидания. [Правила ожидания](no-silent-waits.md)

Например, пока сессия ждёт завершения `npm test`, в списке видно «Ждёт завершения `npm test`», даже если команда ничего не выводит. Если для продолжения нужно разрешение владельца, статус меняется на «Ждёт вашего разрешения».

## Канопус объясняет причину отказа

Если Канопус не распознал входные данные, он должен вернуть код ошибки и объяснить причину отказа. Например, клиент передал неизвестный параметр строки запроса на `/api/*` или `/ws`. Сервер должен вернуть статус HTTP 400 и код `invalid_parameter`. [Формат ошибок API](api-deviations.md)

## Автоматизация обходится без дополнительных запросов к модели

Канопус должен отслеживать сроки и отправлять напоминания с помощью таймеров, сторожей и журнала. Когда наступит время продолжить задачу, Канопус должен запустить следующий рабочий ход агента без отдельного запроса к модели для проверки срока. [ADR-0018](decisions/ADR-0018-process-in-canopus.md)

## Команда обращается к владельцу, когда нужно его решение

Если исполнителю нужны сведения для работы, он обращается к автору задачи. Если автор недоступен, рабочий вопрос решает интегратор проекта. Когда Канон требует решения владельца, интегратор передаёт ему вопрос с рекомендацией и обоснованием. После ответа владельца команда может продолжить работу в пределах полученного разрешения. [ADR-0017](decisions/ADR-0017-working-questions-through-integrator.md)

## Канопус общается с пользователем по правилам технического письма

Канопус должен применять конвенцию технического письма ко всем текстам, которые он показывает или предлагает пользователю. Правило охватывает в том числе вопросы, варианты ответа, уведомления, сообщения об ошибках и подсказки для следующего сообщения. [Конвенция технического письма](https://github.com/unitcraft/engineering-conventions/blob/main/technical-writing.md)

Если пользователю нужно принять решение, Канопус должен ясно сформулировать вопрос и пояснить, что произойдёт при каждом варианте ответа. Когда Канопус предлагает варианты, он должен рекомендовать один из них и кратко объяснить причину. Выбор подтверждает пользователь.

Если Канопус предлагает текст следующего сообщения, он должен сформулировать его от лица пользователя с учётом уже принятых решений. Из текста должно быть понятно, о чём пользователь попросит Канопус, если отправит сообщение.

## Заимствование идеи можно проверить по источнику

При исследовании другого продукта автор разбора указывает точную версию или ревизию и способ проверки. Если идея решает задачу Канопуса, команда может использовать принцип, контракт или формат данных. Команда пишет реализацию самостоятельно, без копирования кода донора. [Правила исследования сторонних продуктов](../research/README.md)

## Маршрут задачи зависит от объёма и риска

При выборе глубины проверки команда должна учитывать и объём работы, и риск ошибки. Для обратимой правки можно применить малый маршрут, если владелец его выбрал и просмотра результата достаточно для приёмки. Если работа требует нескольких самостоятельных результатов, команда предлагает владельцу эпик с отдельными задачами. [ADR-0013](decisions/ADR-0013-proportionality-ahead-of-pin.md) и [правила выбора маршрута](process.md)
